# OpenMusic

The code uses the OpenMusic names: Swift modules (`OpenMusicCore`, `OpenMusicSync`, the `OpenMusic` app target), C# namespaces and projects (`OpenMusic.*`), `OPENMUSIC_*` environment variables and `-OpenMusic*` launch arguments. The old `MEDLEY_*` and `-Medley*` spellings still work as fallbacks (`LaunchEnvironment` in Swift and C#, `scripts/env.sh`). Some strings keep the old name because changing them would break existing installs, saved sign-ins or sync between app versions, so never rename them: the crypto and wire strings both platforms share (`medley.content.v1.*`, `medley.key-exchange.v1.*`, the vault and key formats) and their test vectors, the Convex-Client headers, the fake test sign-in markers, Windows' DPAPI entropy, everything in `Resources/KeychainService/` (its cdhash keeps sign-ins readable), the self-signed identity and its folder on the build Mac, the iPhone's saved device-name setting, and the shared UI lock. User-facing text goes through `ProductInfo.name` (Swift, `Sources/OpenMusicCore/Support/ProductInfo.swift`) and `ProductInfo.Name` (C#, `windows/src/OpenMusic.Core/Support/ProductInfo.cs`).

A native macOS and iOS music player for YouTube Music and Spotify, in the style of Apple Music. Swift 6 + SwiftUI (AppKit where SwiftUI falls short), SwiftPM only, **no third-party dependencies**. Goals in priority order: feels native, fast (instant UI, no spinners for cached content), light (small binary, low idle CPU and memory), complete feature coverage of both services.

If `AGENTS.local.md` exists at the repo root (gitignored), read it too: it holds notes for one person's machines and devices. Machine-specific values for the scripts (SSH targets, signing identity, device ids) live in `scripts/local.env` (gitignored; documented in `scripts/local.env.example`). Before committing, run `scripts/check-public.sh`: with a local `scripts/private-patterns.txt` (gitignored, one extended regex per line) it fails on any tracked line that matches.

## Building

The checkout can live on Linux or a Mac; Apple builds run on a Mac with Xcode 27 and Swift 6.4, reached over SSH (the "build Mac", `OPENMUSIC_MAC_HOST` in `scripts/local.env`). `scripts/mac.sh <slot> '<command>'` rsyncs the checkout to `~/agents/openmusic-<slot>` on the build Mac and runs the command there in a bash login shell. Use your own slot name. On a Mac you can also run the commands directly in the checkout.

```bash
scripts/mac.sh <slot> 'swift build'
scripts/mac.sh <slot> 'swift test'
scripts/mac.sh <slot> 'swift run openmusic-probe ytm search "daft punk"'
scripts/mac.sh <slot> 'scripts/bundle.sh'        # build/OpenMusic.app, signed (see "Mac app: signing")
```

Verify audio playback through player state and time advancing, not by listening: a build machine's speakers may be muted.

## Rules

- No dependencies. Apple frameworks only (Foundation, SwiftUI, AppKit, AVFoundation, MediaPlayer, WebKit, AuthenticationServices, CryptoKit, Security).
- Network and JSON parsing stay off the main actor. Publish results on the main actor.
- Never log or commit tokens, cookies, or account data. Credentials live in the Keychain (`OpenMusicCore.Keychain`).
- Every unsupported provider operation throws `ProviderError.notSupported`, and `capabilities` must say what is supported so the UI can hide it.
- Keep the binary small and idle CPU at zero: no polling timers while paused, no hidden web views unless they are playing.

## Mac app: signing and staying signed in (mac worker)

Sign-ins live in the login Keychain, and macOS lets an item be opened only by the code that saved it: its partition list names the creator, and for an app without an Apple Team ID that is `cdhash:<hash of the binary>`. Ad-hoc builds had a new cdhash every time, so every update signed the listener out. A stable designated requirement alone does not fix that; the partition is still per build. Two pieces keep sign-ins across builds:

- **A stable self-signed identity.** `scripts/signing-identity.sh` (run once on the build Mac; it is idempotent) creates "Medley Self-Signed" in its own keychain, `~/agents/medley-signing/medley-signing.keychain-db`, not the login keychain. The keychain's random password is in `~/agents/medley-signing/keychain-password` (mode 600, directory 700). Never print it, copy it into the repo, or put it in a command's arguments: the process list of the shared build Mac shows every process's arguments to every user. Both scripts hand passwords to `security -i` on stdin and to openssl as `-passout file:`. Builds signed with it have the requirement `identifier "dev.openmusic.OpenMusic" and certificate leaf = H"b5811f6a…"`.
- **A Keychain XPC service that never changes.** `Resources/KeychainService/` (`main.swift` + `Info.plist`) builds `Contents/XPCServices/dev.openmusic.keychain-service.xpc`. The app reads and writes its items through it (`OpenMusicCore.Keychain`, macOS app bundle only; tests, `openmusic-probe`, `swift run` and iOS go direct). `scripts/bundle.sh` builds and signs the bundle once per (hash of both files, certificate) into `~/agents/medley-signing/keychain-service/` and copies it into every build, so its cdhash and the items' partition stay the same. Items live under service `dev.openmusic.keychain`.
  - Who can use it: launchd starts a bundled XPC service only for the app containing it, and the service checks every message's sender with `NSXPCConnection.setCodeSigningRequirement` against `identifier "dev.openmusic.OpenMusic" and certificate leaf = <its own certificate>` (audit token based). An ad-hoc copy of the app is refused ("Received message forbidden due to code signing requirement" in the service's log).
  - Who the app trusts: the app pins the service the same way (`identifier "dev.openmusic.keychain-service" and certificate leaf = <the app's own certificate>` on its `NSXPCConnection`), so a bundle whose service was swapped for other code gets no answers. An app without a certificate uses no service.
  - What it serves: one account at a time (`get`/`set`, no "list everything"), and only the accounts in its allow-list: `spotify.token`, `spotify.account`, `ytm.credentials`, `ytm.account`, `ytm.transfer`, `sync.credentials`, `sync.credentials.installKey`, and the family `sync.credentials.state.<name>`. Anything else gets errSecMissingEntitlement (-34018). The app keeps the same list in `Keychain.accounts` and refuses other names before asking; a test checks the two lists match. The debug probe's `keychain-probe` is served only to builds whose signed Info.plist has `MedleyKeychainProbe` (`CONFIG=debug scripts/bundle.sh` adds it).
  - A new Keychain account (a new provider, a new sync key outside `sync.credentials.state.`) needs the service's list changed, which signs everyone out once (next rule). Prefer a name inside an existing family.
  - `XPCService.JoinExistingSession` must stay true: in its own security session (the default) the service sees the login keychain as locked and every write fails with errSecAuthFailed.
  - Writes update an existing item in place (`SecItemUpdate`, `SecItemAdd` only when missing) and report failure: `Keychain.store` / `storeCodable` throw, `Keychain.set` returns false, and the in-memory copy changes only after the service confirmed the write.
- **Saving and deleting sign-ins report failure.** A sign-in whose credentials the Keychain refused fails (YouTube's `signIn` throws; Spotify shows `.failed`), and nothing changes. `trySignOut()` deletes the saved credentials first and throws, staying signed in, when that fails; Settings › Accounts shows "Couldn't remove the saved sign-in". Plain `signOut()` (used by sync and iOS) also stays signed in on that failure, silently. Cookie and token rotations stay best effort.
- The old stdin/stdout helper (`Contents/Helpers/medley-keychain`, service `app.medley.helper`) is gone, with no migration: no build anyone kept used the helper, and it could be hijacked by a process that spawned it and exec'd OpenMusic. Items it saved on the build Mac are abandoned. Items saved by the first service build (service `app.medley.keychain`) are abandoned too, and so are the pre-rename service's (`app.medley.keychain.v2`, bundle id `app.medley.Medley`): the rename to OpenMusic changed the bundle id, the service and its item name, with no migration.

Rules:

- `scripts/bundle.sh` signs with the identity and embeds the service. If the identity is missing it warns and signs ad-hoc without either; such a build starts signed out every time. Never install an ad-hoc or debug build as the copy someone uses day to day.
- Changing anything in `Resources/KeychainService/` or recreating the identity signs everyone out once (a new cdhash can't open the old items). Don't touch either without a reason, and say so in the commit. When you change the service, also change its `itemService` name: the new binary can't overwrite the old binary's items either, so under the same name every save would fail.
- Proof that a build reads what an earlier build saved (debug builds only: `CONFIG=debug scripts/bundle.sh`; release builds compile the probe out): `OPENMUSIC_KEYCHAIN_PROBE=write|read|acl|delete|refused|unpinned-read OPENMUSIC_SELFTEST_OUT=<file>` (`Sources/OpenMusic/App/KeychainProbe.swift`). It only ever touches the throwaway account `keychain-probe` (and, for `refused`, a name the service must refuse). Launch it with `open -W -n --env ... build/OpenMusic.app` so it runs in the GUI session. `read` turns prompts off, so an item the build can't open reads as missing instead of asking. Change `KeychainProbe.buildMarker` between the write build and the read build so their code differs. `refused` shows the service rejecting an account outside its list; `unpinned-read` skips the app's check of the service, so in a copy whose service was replaced it shows the substitute would have answered while `read` gets nothing.

Home and New cache (`Sources/OpenMusic/App/BrowseDiskCache.swift`, `~/Library/Caches/OpenMusic/browse`): files are keyed by page plus a hash per account the request was sent as, written 0600 in a 0700 folder, and deleted when their account signs out or switches (`BrowseDiskCache.watchAccounts`, started after launch restores sessions, each service judged on its own). Files from older builds are deleted at launch.

- Which account: each provider's `session` (`MusicProvider.session`, `ProviderSession`), which changes only when the credentials its requests carry change, with a new generation each time. Not `authStatus`: while a sign-in replaces an account, `authStatus` is `.signingIn` but requests still carry the old account's credentials. `BrowsePage` keys the page by the sessions it read, refuses to show or save a result when any session changed or was `.changing` before or after the request, and loads again under the new key.
- Credentials never change owner under a session. Spotify's refresh recovery (a refused refresh, after expiry or a 401, answered with another device's rotated token from the sync vault or an incoming import, `SpotifySignInTransfer.recoverRefresh`) hands back a token only with an owner verified with Spotify (`/me` on a throwaway client for the vault's; the import's check for an import), as `SpotifyAPI.RecoveredToken`, and only when that owner is the session's: the API's `userID`, or, before it learned one, the account the provider's session holds. Every owner check is `SpotifyService.me()`, always uncached through `HTTP.uncachedSession` (no URL cache, `.reloadIgnoringLocalAndRemoteCacheData`, no cookie storage, `httpShouldSetCookies` off): restore, a bound write learning its user, the import's and the recovery's checks (`OwnerCheckTests`). Only a definite answer fails closed: `/me` naming another user, or Spotify refusing the candidate token itself (`notSignedIn`); then no token, the refresh counts as revoked and the session ends signed out ("Sign in to do this."). The payload's own `userID` is a claim, never a check. A check that couldn't be made (offline, a timeout, 429, 5xx) throws through `RefreshRecovery` and `refreshToken`: the request fails retryably with the normal notice and Try Again, and the session and its saved token stay. When the check's throwaway client refreshed the vault's token first (spending the vault's refresh token) and then failed, the rotated token is kept on the transfer (`rotatedDuringCheck`) with the owner and session it was checked for, never installed, and checked by the next recovery in that same session. It never outlives them: sign-out and an import drop it, a recovery under any other session or owner drops it unread, and a check that finishes after its session moved on keeps nothing. A kept token that fails its check is only dropped (recovery goes on to the vault): it never ends the current sign-in (`RetainedCandidateTests`). (Not covered: an import whose own check fails that way after rotating still loses the rotation, since the sign-in sync retries the import from the same payload. Keeping it across relaunches needs a new Keychain account name, which the service's allow-list would have to take.) A deliberate switch to another account goes through sign-in or the transfer's import, which start a new session. YouTube's client bumps a credential generation on every replacement (sign-in, swap, sign-out; not a cookie rotation) and applies a response's `Set-Cookie` updates only if the request went out in the current generation (`InnerTubeClient.send`), so a slow answer to account A never rewrites B's cookies (`StaleCookieTests`, with a stub `URLProtocol` through `InnerTubeClient(configuration:)`).
- Ids: `AccountInfo.id` is Spotify's user id and, for YouTube, `datasync:<datasync id>` from the account switcher (`YouTubeMusicProvider.accountID`), never a handle, email or name. Without an id (cookies pasted by hand, or offline with nothing saved) nothing personal goes on disk.
- "Try Again" empties the page cache to force a refresh but keeps the shelves on screen (`ShownResults`) for a service that fails again.

Library lists (Songs, Liked Songs, Albums…) load through `LibraryLoader` (`Sources/OpenMusic/App/LibraryLoader.swift`), one service at a time: each service's complete list is saved under its own key, a failed first page names the service above the other's list ("Couldn't load your Spotify songs", Try Again, or Sign In to that service when its sign-in is gone), a later page that fails is retried and then kept for Try Again, the 200-page limit ends in Load More, and a failed refresh keeps the saved list (never saved as empty). `LibraryLoaderTests` covers each case with `MockProvider.libraryPageFailures`.

Account buttons go through `AppModel.perform(_:)` (`AccountAction`): "Open Accounts…" opens Settings › Accounts; a button naming a service ("Connect Spotify", "Sign In to YouTube Music…") opens that service's own sign-in sheet. The first-run flow (`AppModel.firstRun`, `showOnboarding`; docs/onboarding.md) is for the first launch and Settings › General's "Show Again…" only.

Playback choices take a request number (`AppModel.beginPlayRequest`; a handoff that replaces the queue here, an incoming takeover or Play Here, is one too, through `SyncCoordinator.willReplaceQueue`, so a playlist playing here stops appending its pages; the pause after pushing playback to another device goes through `willRunTransportCommand`); a request that loads before it plays starts only while `canStartPlayRequest` holds: it is still the newest choice and no transport choice came after it. Every transport action (Play/Pause, Next, Previous, seek from the floating, full-screen and mini players, lyrics, Controls menu, Space) goes through `AppModel.togglePlayPause()`/`pause()`/`next()`/`previous()`/`seek(to:)`, the media keys through `NowPlayingCenter.willRunTransportCommand`, and OpenMusic Sync's remote commands (play, pause, toggle, next, previous, stop, seek, takeover; not volume) through `SyncCoordinator.willRunTransportCommand` (`SyncHub.routeTransport`), all counted by `noteTransportChoice`, so Pause while a sorted playlist loads keeps the queue that was there. A playlist that already plays keeps appending its pages after Pause (`isCurrentPlayRequest`). `remainingPlaylistTracks` throws on a failed page and on cancellation: sorted play, shuffle and Play Next/Add to Queue of a playlist then start nothing and show the failure notice with Try Again (for Play Next/Add to Queue of an album, playlist or artist the notice is made at the command, `AppModel.queue(_:next:)`, and Try Again repeats it); a playing playlist whose later page fails keeps playing, and Try Again goes on from that page (`PlaylistPlaybackTests`). Past `maxPlaylistPages` (40 pages, 4,000 songs) with pages left it throws `PlaylistLoadIncomplete` with the part loaded: sorted play, shuffle and the queue commands use that part and say so in a notice that stays until closed ("Only the first 4,000 songs of “X” could be loaded. Playing those."), and a playing playlist that stops appending at the bound says the same; `tracks(for:)` returns the part marked (`ResolvedTracks.part`) and shows nothing, so a drop on Playing Next or on a playlist publishes one notice ("Added the first 4,000 songs of “X” to the queue", "… to “P”"); nothing passes a part off as the whole playlist. Notices expire on `AppModel.noticeSleep` (tests pass a clock they advance and await `noticeExpiry`); drops keep their work in `lastDrop` and playlist edits in `lastPlaylistEdit`, so tests await the work instead of sleeping.

## Mac app: frame timing (mac worker)

Release builds have no test hooks: every `OPENMUSIC_SELFTEST` self-test (`fullscreen`, `inspector`, `inspectorwidth`, `resize`, `find`, `menus`, `launch`, `hover`, `layout`, `lyrics`, `tour`), the council captures (`CouncilShots`), the sync self-test and the fake test sign-ins (`testPayload`, `acceptingTestSignIns`) are behind `#if DEBUG`, except `sidebar` and `sidebarscroll`, which this benchmark and `scripts/sidebar-bench.sh` run on Release builds: the accepted exceptions (they only move the sidebar on mock data and touch no account, key or sync state). So is the snapshot runner (`OPENMUSIC_SNAPSHOT_DIR`, `SnapshotRunner`): snapshot scripts build Debug (`CONFIG=debug scripts/bundle.sh`). `scripts/check-release-hooks.sh` (after a release `scripts/bundle.sh`) checks the binary for them.

`OPENMUSIC_MOCK=1 OPENMUSIC_SELFTEST=sidebar OPENMUSIC_SELFTEST_OUT=<file>` hides and shows the sidebar six times on Home, New, an album, an artist and Songs and records every frame with a display link: frames per move, the longest gap, dropped frames. The build Mac is shared: wait for the 5-minute load average to drop below about 6 before comparing runs, or the numbers are noise. Pages should stay lazy (`ScrollPage` uses a `LazyVStack`): a plain `VStack` of shelves lays out every shelf on each frame of a resize or sidebar move. Geometry that moves with a slide and only feeds a decision goes in a non-observable holder, with only the decision as `@State`, written when it flips (`ArtistHero`'s `HeroGeometry` and `darkText`).

`OPENMUSIC_SELFTEST=lyrics` does the same for the lyrics and queue panel (open and close at 1440 and 1200, lyrics already loaded, 80 lines, and still loading) and first records the main thread's CPU time with nothing moving, playing and paused. `OPENMUSIC_SELFTEST_LYRICS=1200:queue,…` runs only some cases, and each toggle is a Points of Interest signpost, so an `xctrace` Time Profiler run can be cut to the moves. Attach xctrace to a running pid (`--attach`): `--launch` of a bundle path can start another checkout's OpenMusic.app with the same bundle id.

The play button's buffering ring (`PlayPauseButton`, shared by the floating, mini and full-screen players) shows only after 0.5 s of continuous buffering (one delayed state flip in a `.task(id:)`, cancelled when buffering ends): a faint full track with an arc on the disc's edge, in the glyph's ink, turned by Core Animation (`SpinnerRing`), still with Reduce Motion. The rotation runs only while the ring's view is in a window and not hidden (taken off when it leaves, hides or is dismantled), and the floating player's hidden measuring copies (`isPlayerMeasurement`) never watch buffering at all (`PlayPauseButton.tracksBuffering`). Council captures wait in `settle` until buffering ends, so no shot catches the ring by chance (`council.txt` logs the waits); `fullscreen-buffering` forces the state (`AppModel.debugForcesBuffering`, Debug only) and checks the ring is absent at 0.3 s and drawn at 0.9 s (PASS/FAIL).

Nothing may animate through SwiftUI for as long as music plays: any SwiftUI animation that runs every frame (a repeating `.symbolEffect`, a `withAnimation` glide, `repeatForever`) re-renders and lays out the whole window each frame, about a quarter of a core, and every panel, sidebar and scroll animation then drops frames. The playing row's bars (`NowPlayingIndicator`) and the timeline's glide (`Scrubber`) run in Core Animation for that reason; the mini player's progress line (2 pt on the strip under the artwork, in the strip's title ink, the rest at 18%) is a scale of the player's time with no animation; idle-while-playing should stay near 35 ms of main thread per second.

Reduce Motion: custom transitions and in-place expansions go through `Motion.Transition` and `Motion.Expansion` (`Design/Theme.swift`): with Reduce Motion every transition is a plain crossfade and every expansion immediate; press, hover and paused scales use `motionScale` (none with Reduce Motion) and disclosure chevrons `DisclosureChevron` (swapped, not rotated). The full-screen player opens and closes only through `AppModel.setFullScreenPlayerPresented`. Add a new case there rather than a bare `.transition(.offset…)` or `withAnimation`; `ReduceMotionTests` checks every case.

## Mac app: column widths (mac worker)

On macOS 26 and later the page's column runs under the sidebar and the lyrics/queue panel, and SwiftUI measures its minimum inside those insets, counting the sidebar twice: the window needs 420 + 2 × sidebar + panel (`SplitViewTuning.neededWidth`; on macOS 15 the columns sit side by side and the sidebar counts once, `sidebarShare`). AppKit can't narrow a column to meet that, so in a narrower window it aborts ("more Update Constraints in Window passes than there are views in the window") or, without a panel, pushes the split view past the window's edge. `AppModel` keeps the columns inside the window: on every window resize (synchronously, before layout) the panel and then the sidebar narrow, and the sidebar hides when a panel still doesn't fit; divider drags are capped (`limitColumnWidths`); opening a panel and widening lyrics use the same arithmetic: lyrics get their 420 pt ideal (the reading width) only in a window of at least 1300 pt with room for 420 beside the sidebar as AppKit has it (1306 pt beside a 232 pt sidebar on macOS 26), otherwise they open at 310 and the divider moves to the room left (`AppModel.sizeInspector`). The panel column's maximum is also chosen in the update that opens it (`AppModel.inspectorMaxWidth`: the room beside the sidebar it keeps, at most 520; back to 520 once closed): AppKit can bring the column back at its last width, and SwiftUI applies its own maximum as it presents the panel, so lyrics dragged to 520 reopened at 498 pt beside a 232 pt sidebar in a 1220 pt window and AppKit aborted. That maximum doesn't hold the column on its own: a 520 pt drag made while the sidebar was hidden stays the column's wanted width after it closes, AppKit brought it back at 387–520 pt beside the 232 pt sidebar in a 1220 pt window whatever the maximum (1406 pt needed; about 4 runs of 10 of the `toggle` cases at 1200 and 1220 aborted), and a panel held at its maximum sprang to 520 the moment the sidebar hid. Moving the divider is what changes that width (lowering the closed column's maximum or its view's frame did not), so a panel that may come back wider than the room beside the sidebar in its window has its divider moved back to 310 just before it closes, by every path (`AppModel.normalizePanelBeforeClose`). As a fallback, `SplitViewTuning.panelRestoreBound` keeps the widest the column has shown since it was made or last narrowed that way (open or closed; the closed column's frame alone read 310, then 520 40 ms later), and opening a panel whose bound doesn't fit beside the sidebar hides it (`AppModel.fitInspector`). SwiftUI writes each presentation back through the inspector binding when its transaction ends (`true` about 250 ms after an open, `false` 300–400 ms after a close), and a panel reopened before the `false` of the close arrived was closed again by it (60 of 96 reopens 50–150 ms after a close). So a reopen within 1.5 s of a close waits until SwiftUI has written that close back and the sidebar it brings back is in (`AppModel.toggleInspector`, `reopenMustWait`), then opens; the binding's `false` reaches the model through `inspectorPresentationEnded`. Every user action goes through the model, so closes and ordinary opens never wait.

The sidebar and a panel share the window only when both fit. Otherwise the one asked for last wins, as in Music: opening a panel (counted at the width it comes back at) or narrowing the window hides the sidebar (narrowing keeps it down to 1112 pt on macOS 26, the sidebar at 190 beside the panel at 310; 922 on macOS 15), showing the sidebar closes a panel it doesn't fit beside, and closing a panel brings back a sidebar it hid. Showing the sidebar takes room for its 232 pt ideal width (`SplitViewTuning.sidebarIdealWidth`, which `SidebarMetrics.idealWidth` and the column use; SwiftUI brings it back at that width; with less room the sidebar's and the panel's caps chase each other) beside the panel's current width, at least 310: 1196 pt on macOS 26, 964 on macOS 15 (`SplitViewTuning.sidebarFitsBesidePanel`). The sidebar's search (`revealSearch`) follows the same rule. It never resizes the panel. Every way of showing the sidebar goes through `AppModel.showSidebarBesidePanel` before AppKit lays the column out: the toolbar's button and View › Show Sidebar (⌃⌘S, our own command in place of `SidebarCommands`, whose item AppKit applied directly) set `columnVisibility`, and anything that uncollapses the column in AppKit arrives through key-value observing of the sidebar's split view item.

While the sidebar's column animates in (from the moment that observation sees it uncollapse, for 0.8 s; the animation takes about 0.5 s), the main window can't get narrower than it was when the animation began (`SidebarAnimationGuard`, which exchanges `NSWindow.setFrame(_:display:)` and `setFrame(_:display:animate:)` once; live resizing goes through them too). Only intent counts as what the window should become (`ShrinkDeferral`): the user's live resize, a zoom, tile or script (their first caller outside OpenMusic is AppKit) and the app's own frames, which go through `NSWindow.requestFrame` (use it for every frame the app sets on the main window: app code can run under SwiftUI, in a `.task` or a button's action, and would look like SwiftUI's). A narrower intent is clamped to that width and applied when the guard ends; a wider one goes through at once and stays the window's size. SwiftUI's own frames (`NSHostingView.updateAnimatedWindowSize`, from `windowDidLayout`, told apart by their first caller outside OpenMusic) are never remembered and can't take the window below that width or below the latest intent: 150 ms into the animation SwiftUI set a window just widened to 1300 back to 960 and stepped it toward 955, which the guard used to apply at its end. With no intent the guard applies nothing at its end. A shrink to 900 pt mid-animation made SwiftUI grow the window by the width it lost, pass after pass, until AppKit aborted, although the columns fit 900. SwiftUI owns the window's delegate, so `windowWillResize` isn't an option. In native full screen the window can't grow, so showing the sidebar beside a panel where both fit is left to SwiftUI (the AppKit restore skips full screen and used to loop with the binding). After AppKit shows the sidebar and closes a panel, only a widening AppKit itself made is put back, and only if nothing has resized the window since (`WidthCorrection`: `setFrame` calls, live resize and full screen move its stamp). At launch the split view's autosave can restore the sidebar collapsed while `columnVisibility` starts at `.all`; the binding takes AppKit's state and the sidebar comes back through AppKit at the window's width (`adoptRestoredSidebar`), and the columns are fitted as soon as the window is watched. View › Show/Hide Sidebar is enabled only while the main window is open and key or main (`canToggleSidebar`); SwiftUI refreshes its menu items only as a menu opens (`menuNeedsUpdate`), so a test that reads or chooses one must call that first.

No read can rule out a write landing between the check and the insert: without the service checking a version on the write itself, a concurrent change in that window can still shift a place. Each edit belongs to the account it began under (`PlaylistEditAccount`: the service and its immutable account id; without an id, the exact `ProviderSession`), not to the token: a refresh or a sign-in synced from another device for the same account keeps the edit and its Undo. Before every request the service must send as that account with no swap under way (`canSend`, which needs a current `.account` session in both of its branches; a swap in progress, `.changing`, stops the run with "Your Spotify sign-in was changing." and Try Again, nothing sent), and after every wait a run whose account the service no longer holds stops silently. That main-actor check isn't enough on its own: the write crosses into `@concurrent` service code and the API actor, where a synced sign-in can install another account's token first. So every playlist write (remove, insert, append, Add to Playlist, New Playlist and its songs) goes through the bound calls `MusicProvider.add/remove/insert/createPlaylist(…, as: PlaylistWriteAccount)`: the provider checks the account on the main actor and turns it into a binding (Spotify: `SpotifyWriteBinding`, the user id, or without one the provider's token-swap epoch; YouTube: `YTMWriteBinding`, the datasync account id or the credential-swap epoch), and the network actor checks it again where it picks the credentials, for every chunk, retry and attempt, with nothing suspending between that check and the send (`SpotifyAPI.data`, `InnerTubeClient.post`/`checkWriteBinding`). A mismatch sends nothing and throws `PlaylistEditError.accountChanged` (the same "sign-in was changing" notice with Try Again). A new token for the same user still writes (a bound Spotify write whose session moved to the same user's new token goes again with it); before a bound Spotify write the API learns whose token it holds from `/me` if it doesn't know. No edit starts during a swap: `beginPlaylistEdit` refuses with that notice and Try Again, and the confirmation's count and New Playlist do too. New Playlist keeps the playlist once the service acknowledged it: if adding its songs fails, Try Again adds them to that playlist (`fillNewPlaylist`), never making a second one (`NewPlaylistBindingTests`). The songs go in requests of the service's batch size and the record (`NewPlaylistFill`) keeps what each acknowledged, so Try Again sends only what is pending; after a failure that may have landed anyway (`writeMayHaveLanded`: a timeout or a 5xx, not offline, 429, 401 or an account refusal) it first reads the playlist uncached and whole and sends only the pending songs it doesn't hold, as Add Back at End (`NewPlaylistFillTests`). Recovery actions (Add Back at End and its Try Again, Try Again, Undo) keep the original edit's account and never take the current one.
