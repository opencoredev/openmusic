# OpenMusic: notes for coding agents

This file is for coding agents, and anyone changing the code: the architecture, the invariants a change must keep, and the rules. How to build and test from a fresh clone is in [CONTRIBUTING.md](CONTRIBUTING.md). The maintainers' remote build machines, deployments and screenshot tooling are in [docs/maintainers.md](docs/maintainers.md); how the code got here is in [docs/history.md](docs/history.md).

If `AGENTS.local.md` exists at the repo root (gitignored), read it too: it holds notes for one person's machines and devices. Machine-specific values for the scripts (SSH targets, signing identity, device ids) live in `scripts/local.env` (gitignored; documented in `scripts/local.env.example`). Before committing, run `scripts/check-public.sh`: with a local `scripts/private-patterns.txt` (gitignored, one extended regex per line) it fails on any tracked line that matches. CI also scans every commit with gitleaks (`.gitleaks.toml`).

A native macOS, iOS and Windows music player for YouTube Music and Spotify, in the style of Apple Music. On Apple platforms: Swift 6 + SwiftUI (AppKit where SwiftUI falls short), SwiftPM only, **no third-party dependencies**. Goals in priority order: feels native, fast (instant UI, no spinners for cached content), light (small binary, low idle CPU and memory), complete feature coverage of both services.

## Names

The code uses the OpenMusic names: Swift modules (`OpenMusicCore`, `OpenMusicSync`, the `OpenMusic` app target), C# namespaces and projects (`OpenMusic.*`), `OPENMUSIC_*` environment variables and `-OpenMusic*` launch arguments. The old `MEDLEY_*` and `-Medley*` spellings still work as fallbacks (`LaunchEnvironment` in Swift and C#, `scripts/env.sh`). Some strings keep the old name because changing them would break existing installs, saved sign-ins or sync between app versions, so never rename them: the crypto and wire strings both platforms share (`medley.content.v1.*`, `medley.key-exchange.v1.*`, the vault and key formats) and their test vectors, the Convex-Client headers, the fake test sign-in markers, Windows' DPAPI entropy, everything in `Resources/KeychainService/` (its cdhash keeps sign-ins readable), the self-signed identity and its folder (`~/agents/medley-signing`), the iPhone's saved device-name setting, and the shared UI lock. User-facing text goes through `ProductInfo.name` (Swift, `Sources/OpenMusicCore/Support/ProductInfo.swift`) and `ProductInfo.Name` (C#, `windows/src/OpenMusic.Core/Support/ProductInfo.cs`).

## Building and checking

`swift build`, `swift test` and `scripts/bundle.sh` (build/OpenMusic.app) on a Mac with Xcode 27 ([CONTRIBUTING.md](CONTRIBUTING.md)). From a Linux checkout, `scripts/mac.sh <slot> '<command>'` runs the same commands on a Mac over SSH ([docs/maintainers.md](docs/maintainers.md#build-mac)).

- Verify audio playback through player state and time advancing, not by listening: a build machine's speakers may be muted.
- Shared targets (`OpenMusicCore`, `YouTubeMusicKit`, `SpotifyKit`, `OpenMusicSync`) build for macOS and iOS. Put AppKit-only code behind `#if os(macOS)` and give iOS its own path.
- The iOS app is built from `iOS/project.yml` with XcodeGen and runs in the iOS Simulator. On a shared Mac, make your own simulator (`xcrun simctl create agent-<slot> "iPhone 17 Pro"`), address it by UDID, and delete it when you finish. Never `simctl shutdown all`, `erase all`, or `killall Simulator`.
- Screenshots that go in the repository use only the sample data (invented artists, procedural covers): `scripts/demo-shots.sh` with its default `OPENMUSIC_DEMO_DATA=sample`. Never commit real album art, artist photos or the chart-album demo data's images.

## Sync backend and accounts

- Devices sync by signing in with Clerk ([docs/accounts-design.md](docs/accounts-design.md)); a self-hoster gives the apps one server URL ([docs/self-hosting.md](docs/self-hosting.md); `sync/self-host/` has the compose file and `deploy.sh`). Every deployment needs `CLERK_JWT_ISSUER_DOMAIN` and `CLERK_PUBLISHABLE_KEY` set before backend changes deploy.
- The hosted beta has a dev deployment (Debug builds, tests, self-tests) and a production one (Release builds); `scripts/bundle.sh` and `iOS/project.yml` set `OpenMusicSyncURL` per configuration. Backend changes go to production only after they pass on dev. Deploying, the Clerk instance and test users: [docs/maintainers.md](docs/maintainers.md#convex-deployments).
- The Clerk secret key is only for Clerk Backend API calls from a maintainer's machine: never printed, committed, or put in the apps or a Convex deployment.

## Windows app and C# core

`windows/` holds OpenMusic for Windows (WinUI 3, .NET 10) and `OpenMusic.Core`, a cross-platform C# port of `OpenMusicCore` that builds and tests on Linux (`dotnet test windows/OpenMusic.Core.slnf`). Layout and porting rules: [windows/AGENTS.md](windows/AGENTS.md); build, run and snapshots: [windows/README.md](windows/README.md). ## Rules

- No dependencies. Apple frameworks only (Foundation, SwiftUI, AppKit, AVFoundation, MediaPlayer, WebKit, AuthenticationServices, CryptoKit, Security).
- Network and JSON parsing stay off the main actor. Publish results on the main actor.
- Never log or commit tokens, cookies, or account data. Credentials live in the Keychain (`OpenMusicCore.Keychain`).
- Every unsupported provider operation throws `ProviderError.notSupported`, and `capabilities` must say what is supported so the UI can hide it.
- Keep the binary small and idle CPU at zero: no polling timers while paused, no hidden web views unless they are playing.

## Mac app: signing and staying signed in

Sign-ins live in the login Keychain, and macOS lets an item be opened only by the code that saved it: its partition list names the creator, and for an app without an Apple Team ID that is `cdhash:<hash of the binary>`. Ad-hoc builds had a new cdhash every time, so every update signed the listener out. A stable designated requirement alone does not fix that; the partition is still per build. Two pieces keep sign-ins across builds:

- **A stable self-signed identity.** `scripts/signing-identity.sh` (run once on the Mac that builds; it is idempotent) creates "Medley Self-Signed" in its own keychain, `~/agents/medley-signing/medley-signing.keychain-db`, not the login keychain. The keychain's random password is in `~/agents/medley-signing/keychain-password` (mode 600, directory 700). Never print it, copy it into the repo, or put it in a command's arguments: on a shared Mac the process list shows every process's arguments to every user. Both scripts hand passwords to `security -i` on stdin and to openssl as `-passout file:`. Builds signed with it have the requirement `identifier "dev.openmusic.OpenMusic" and certificate leaf = H"b5811f6a…"`.
- **A Keychain XPC service that never changes.** `Resources/KeychainService/` (`main.swift` + `Info.plist`) builds `Contents/XPCServices/dev.openmusic.keychain-service.xpc`. The app reads and writes its items through it (`OpenMusicCore.Keychain`, macOS app bundle only; tests, `openmusic-probe`, `swift run` and iOS go direct). `scripts/bundle.sh` builds and signs the bundle once per (hash of both files, certificate) into `~/agents/medley-signing/keychain-service/` and copies it into every build, so its cdhash and the items' partition stay the same. Items live under service `dev.openmusic.keychain`.
  - Who can use it: launchd starts a bundled XPC service only for the app containing it, and the service checks every message's sender with `NSXPCConnection.setCodeSigningRequirement` against `identifier "dev.openmusic.OpenMusic" and certificate leaf = <its own certificate>` (audit token based). An ad-hoc copy of the app is refused ("Received message forbidden due to code signing requirement" in the service's log).
  - Who the app trusts: the app pins the service the same way (`identifier "dev.openmusic.keychain-service" and certificate leaf = <the app's own certificate>` on its `NSXPCConnection`), so a bundle whose service was swapped for other code gets no answers. An app without a certificate uses no service.
  - What it serves: one account at a time (`get`/`set`, no "list everything"), and only the accounts in its allow-list: `spotify.token`, `spotify.account`, `ytm.credentials`, `ytm.account`, `ytm.transfer`, `sync.credentials`, `sync.credentials.installKey`, and the family `sync.credentials.state.<name>`. Anything else gets errSecMissingEntitlement (-34018). The app keeps the same list in `Keychain.accounts` and refuses other names before asking; a test checks the two lists match. The debug probe's `keychain-probe` is served only to builds whose signed Info.plist has `MedleyKeychainProbe` (`CONFIG=debug scripts/bundle.sh` adds it).
  - A new Keychain account (a new provider, a new sync key outside `sync.credentials.state.`) needs the service's list changed, which signs everyone out once (next rule). Prefer a name inside an existing family.
  - `XPCService.JoinExistingSession` must stay true: in its own security session (the default) the service sees the login keychain as locked and every write fails with errSecAuthFailed.
  - Writes update an existing item in place (`SecItemUpdate`, `SecItemAdd` only when missing) and report failure: `Keychain.store` / `storeCodable` throw, `Keychain.set` returns false, and the in-memory copy changes only after the service confirmed the write.
- **Saving and deleting sign-ins report failure.** A sign-in whose credentials the Keychain refused fails (YouTube's `signIn` throws; Spotify shows `.failed`), and nothing changes. `trySignOut()` deletes the saved credentials first and throws, staying signed in, when that fails; Settings › Accounts shows "Couldn't remove the saved sign-in". Plain `signOut()` (used by sync and iOS) also stays signed in on that failure, silently. Cookie and token rotations stay best effort.
- Items saved under older service names (`app.medley.helper`, `app.medley.keychain`, `app.medley.keychain.v2`, bundle id `app.medley.Medley`) are abandoned: there is no migration, and nothing may read them ([history](docs/history.md#keychain)).

Rules:

- `scripts/bundle.sh` signs with the identity and embeds the service. If the identity is missing it warns and signs ad-hoc without either; such a build starts signed out every time. Never install an ad-hoc or debug build as the copy someone uses day to day.
- Changing anything in `Resources/KeychainService/` or recreating the identity signs everyone out once (a new cdhash can't open the old items). Don't touch either without a reason, and say so in the commit. When you change the service, also change its `itemService` name: the new binary can't overwrite the old binary's items either, so under the same name every save would fail.
- Proof that a build reads what an earlier build saved (debug builds only: `CONFIG=debug scripts/bundle.sh`; release builds compile the probe out): `OPENMUSIC_KEYCHAIN_PROBE=write|read|acl|delete|refused|unpinned-read OPENMUSIC_SELFTEST_OUT=<file>` (`Sources/OpenMusic/App/KeychainProbe.swift`). It only ever touches the throwaway account `keychain-probe` (and, for `refused`, a name the service must refuse). Launch it with `open -W -n --env ... build/OpenMusic.app` so it runs in the GUI session. `read` turns prompts off, so an item the build can't open reads as missing instead of asking. Change `KeychainProbe.buildMarker` between the write build and the read build so their code differs. `refused` shows the service rejecting an account outside its list; `unpinned-read` skips the app's check of the service, so in a copy whose service was replaced it shows the substitute would have answered while `read` gets nothing.

Home and New cache (`Sources/OpenMusic/App/BrowseDiskCache.swift`, `~/Library/Caches/OpenMusic/browse`): files are keyed by page plus a hash per account the request was sent as, written 0600 in a 0700 folder, and deleted when their account signs out or switches (`BrowseDiskCache.watchAccounts`, started after launch restores sessions, each service judged on its own). Files from older builds are deleted at launch.

- Which account: each provider's `session` (`MusicProvider.session`, `ProviderSession`), which changes only when the credentials its requests carry change, with a new generation each time. Not `authStatus`: while a sign-in replaces an account, `authStatus` is `.signingIn` but requests still carry the old account's credentials. `BrowsePage` keys the page by the sessions it read, refuses to show or save a result when any session changed or was `.changing` before or after the request, and loads again under the new key.
- Credentials never change owner under a session. Spotify's refresh recovery (a refused refresh, after expiry or a 401, answered with another device's rotated token from the sync vault or an incoming import, `SpotifySignInTransfer.recoverRefresh`) hands back a token only with an owner verified with Spotify (`/me` on a throwaway client for the vault's; the import's check for an import), as `SpotifyAPI.RecoveredToken`, and only when that owner is the session's: the API's `userID`, or, before it learned one, the account the provider's session holds. Every owner check is `SpotifyService.me()`, always uncached through `HTTP.uncachedSession` (no URL cache, `.reloadIgnoringLocalAndRemoteCacheData`, no cookie storage, `httpShouldSetCookies` off): restore, a bound write learning its user, the import's and the recovery's checks (`OwnerCheckTests`). Only a definite answer fails closed: `/me` naming another user, or Spotify refusing the candidate token itself (`notSignedIn`); then no token, the refresh counts as revoked and the session ends signed out ("Sign in to do this."). The payload's own `userID` is a claim, never a check. A check that couldn't be made (offline, a timeout, 429, 5xx) throws through `RefreshRecovery` and `refreshToken`: the request fails retryably with the normal notice and Try Again, and the session and its saved token stay. When the check's throwaway client refreshed the vault's token first (spending the vault's refresh token) and then failed, the rotated token is kept on the transfer (`rotatedDuringCheck`) with the owner and session it was checked for, never installed, and checked by the next recovery in that same session. It never outlives them: sign-out and an import drop it, a recovery under any other session or owner drops it unread, and a check that finishes after its session moved on keeps nothing. A kept token that fails its check is only dropped (recovery goes on to the vault): it never ends the current sign-in (`RetainedCandidateTests`). (Not covered: an import whose own check fails that way after rotating still loses the rotation, since the sign-in sync retries the import from the same payload. Keeping it across relaunches needs a new Keychain account name, which the service's allow-list would have to take.) A deliberate switch to another account goes through sign-in or the transfer's import, which start a new session. YouTube's client bumps a credential generation on every replacement (sign-in, swap, sign-out; not a cookie rotation) and applies a response's `Set-Cookie` updates only if the request went out in the current generation (`InnerTubeClient.send`), so a slow answer to account A never rewrites B's cookies (`StaleCookieTests`, with a stub `URLProtocol` through `InnerTubeClient(configuration:)`).
- Ids: `AccountInfo.id` is Spotify's user id and, for YouTube, `datasync:<datasync id>` from the account switcher (`YouTubeMusicProvider.accountID`), never a handle, email or name. Without an id (cookies pasted by hand, or offline with nothing saved) nothing personal goes on disk.
- "Try Again" empties the page cache to force a refresh but keeps the shelves on screen (`ShownResults`) for a service that fails again.

Library lists (Songs, Liked Songs, Albums…) load through `LibraryLoader` (`Sources/OpenMusic/App/LibraryLoader.swift`), one service at a time: each service's complete list is saved under its own key, a failed first page names the service above the other's list ("Couldn't load your Spotify songs", Try Again, or Sign In to that service when its sign-in is gone), a later page that fails is retried and then kept for Try Again, the 200-page limit ends in Load More, and a failed refresh keeps the saved list (never saved as empty). `LibraryLoaderTests` covers each case with `MockProvider.libraryPageFailures`.

Account buttons go through `AppModel.perform(_:)` (`AccountAction`): "Open Accounts…" opens Settings › Accounts; a button naming a service ("Connect Spotify", "Sign In to YouTube Music…") opens that service's own sign-in sheet. The first-run flow (`AppModel.firstRun`, `showOnboarding`; docs/onboarding.md) is for the first launch and Settings › General's "Show Again…" only.

Playback choices take a request number (`AppModel.beginPlayRequest`; a handoff that replaces the queue here, an incoming takeover or Play Here, is one too, through `SyncCoordinator.willReplaceQueue`, so a playlist playing here stops appending its pages; the pause after pushing playback to another device goes through `willRunTransportCommand`); a request that loads before it plays starts only while `canStartPlayRequest` holds: it is still the newest choice and no transport choice came after it. Every transport action (Play/Pause, Next, Previous, seek from the floating, full-screen and mini players, lyrics, Controls menu, Space) goes through `AppModel.togglePlayPause()`/`pause()`/`next()`/`previous()`/`seek(to:)`, the media keys through `NowPlayingCenter.willRunTransportCommand`, and OpenMusic Sync's remote commands (play, pause, toggle, next, previous, stop, seek, takeover; not volume) through `SyncCoordinator.willRunTransportCommand` (`SyncHub.routeTransport`), all counted by `noteTransportChoice`, so Pause while a sorted playlist loads keeps the queue that was there. A playlist that already plays keeps appending its pages after Pause (`isCurrentPlayRequest`). `remainingPlaylistTracks` throws on a failed page and on cancellation: sorted play, shuffle and Play Next/Add to Queue of a playlist then start nothing and show the failure notice with Try Again (for Play Next/Add to Queue of an album, playlist or artist the notice is made at the command, `AppModel.queue(_:next:)`, and Try Again repeats it); a playing playlist whose later page fails keeps playing, and Try Again goes on from that page (`PlaylistPlaybackTests`). Past `maxPlaylistPages` (40 pages, 4,000 songs) with pages left it throws `PlaylistLoadIncomplete` with the part loaded: sorted play, shuffle and the queue commands use that part and say so in a notice that stays until closed ("Only the first 4,000 songs of “X” could be loaded. Playing those."), and a playing playlist that stops appending at the bound says the same; `tracks(for:)` returns the part marked (`ResolvedTracks.part`) and shows nothing, so a drop on Playing Next or on a playlist publishes one notice ("Added the first 4,000 songs of “X” to the queue", "… to “P”"); nothing passes a part off as the whole playlist. Notices expire on `AppModel.noticeSleep` (tests pass a clock they advance and await `noticeExpiry`); drops keep their work in `lastDrop` and playlist edits in `lastPlaylistEdit`, so tests await the work instead of sleeping.

## Mac app: frame timing

Release builds have no test hooks: every `OPENMUSIC_SELFTEST` self-test (`fullscreen`, `inspector`, `inspectorwidth`, `resize`, `find`, `menus`, `launch`, `hover`, `layout`, `lyrics`, `tour`), the council captures (`CouncilShots`), the sync self-test and the fake test sign-ins (`testPayload`, `acceptingTestSignIns`) are behind `#if DEBUG`, except `sidebar` and `sidebarscroll`, which this benchmark and `scripts/sidebar-bench.sh` run on Release builds: the accepted exceptions (they only move the sidebar on mock data and touch no account, key or sync state). So is the snapshot runner (`OPENMUSIC_SNAPSHOT_DIR`, `SnapshotRunner`): snapshot scripts build Debug (`CONFIG=debug scripts/bundle.sh`). `scripts/check-release-hooks.sh` (after a release `scripts/bundle.sh`) checks the binary for them.

`OPENMUSIC_MOCK=1 OPENMUSIC_SELFTEST=sidebar OPENMUSIC_SELFTEST_OUT=<file>` hides and shows the sidebar six times on Home, New, an album, an artist and Songs and records every frame with a display link: frames per move, the longest gap, dropped frames. On a shared Mac, wait for the 5-minute load average to drop below about 6 before comparing runs, or the numbers are noise. Pages should stay lazy (`ScrollPage` uses a `LazyVStack`): a plain `VStack` of shelves lays out every shelf on each frame of a resize or sidebar move. Geometry that moves with a slide and only feeds a decision goes in a non-observable holder, with only the decision as `@State`, written when it flips (`ArtistHero`'s `HeroGeometry` and `darkText`).

`OPENMUSIC_SELFTEST=lyrics` does the same for the lyrics and queue panel (open and close at 1440 and 1200, lyrics already loaded, 80 lines, and still loading) and first records the main thread's CPU time with nothing moving, playing and paused. `OPENMUSIC_SELFTEST_LYRICS=1200:queue,…` runs only some cases, and each toggle is a Points of Interest signpost, so an `xctrace` Time Profiler run can be cut to the moves. Attach xctrace to a running pid (`--attach`): `--launch` of a bundle path can start another checkout's OpenMusic.app with the same bundle id.

The play button's buffering ring (`PlayPauseButton`, shared by the floating, mini and full-screen players) shows only after 0.5 s of continuous buffering (one delayed state flip in a `.task(id:)`, cancelled when buffering ends): a faint full track with an arc on the disc's edge, in the glyph's ink, turned by Core Animation (`SpinnerRing`), still with Reduce Motion. The rotation runs only while the ring's view is in a window and not hidden (taken off when it leaves, hides or is dismantled), and the floating player's hidden measuring copies (`isPlayerMeasurement`) never watch buffering at all (`PlayPauseButton.tracksBuffering`). Review captures (`CouncilShots`) wait in `settle` until buffering ends, so no shot catches the ring by chance (`council.txt` logs the waits); `fullscreen-buffering` forces the state (`AppModel.debugForcesBuffering`, Debug only) and checks the ring is absent at 0.3 s and drawn at 0.9 s (PASS/FAIL).

Nothing may animate through SwiftUI for as long as music plays: any SwiftUI animation that runs every frame (a repeating `.symbolEffect`, a `withAnimation` glide, `repeatForever`) re-renders and lays out the whole window each frame, about a quarter of a core, and every panel, sidebar and scroll animation then drops frames. The playing row's bars (`NowPlayingIndicator`) and the timeline's glide (`Scrubber`) run in Core Animation for that reason; the mini player's progress line (2 pt on the strip under the artwork, in the strip's title ink, the rest at 18%) is a scale of the player's time with no animation; idle-while-playing should stay near 35 ms of main thread per second.

Reduce Motion: custom transitions and in-place expansions go through `Motion.Transition` and `Motion.Expansion` (`Design/Theme.swift`): with Reduce Motion every transition is a plain crossfade and every expansion immediate; press, hover and paused scales use `motionScale` (none with Reduce Motion) and disclosure chevrons `DisclosureChevron` (swapped, not rotated). The full-screen player opens and closes only through `AppModel.setFullScreenPlayerPresented`. Add a new case there rather than a bare `.transition(.offset…)` or `withAnimation`; `ReduceMotionTests` checks every case.

## Mac app: column widths

On macOS 26 and later the page's column runs under the sidebar and the lyrics/queue panel, and SwiftUI measures its minimum inside those insets, counting the sidebar twice: the window needs 420 + 2 × sidebar + panel (`SplitViewTuning.neededWidth`; on macOS 15 the columns sit side by side and the sidebar counts once, `sidebarShare`). AppKit can't narrow a column to meet that, so in a narrower window it aborts ("more Update Constraints in Window passes than there are views in the window") or, without a panel, pushes the split view past the window's edge. `AppModel` keeps the columns inside the window: on every window resize (synchronously, before layout) the panel and then the sidebar narrow, and the sidebar hides when a panel still doesn't fit; divider drags are capped (`limitColumnWidths`); opening a panel and widening lyrics use the same arithmetic: lyrics get their 420 pt ideal (the reading width) only in a window of at least 1300 pt with room for 420 beside the sidebar as AppKit has it (1306 pt beside a 232 pt sidebar on macOS 26), otherwise they open at 310 and the divider moves to the room left (`AppModel.sizeInspector`). The panel column's maximum is also chosen in the update that opens it (`AppModel.inspectorMaxWidth`: the room beside the sidebar it keeps, at most 520; back to 520 once closed): AppKit can bring the column back at its last width, and SwiftUI applies its own maximum as it presents the panel, so lyrics dragged to 520 reopened at 498 pt beside a 232 pt sidebar in a 1220 pt window and AppKit aborted. That maximum doesn't hold the column on its own: a 520 pt drag made while the sidebar was hidden stays the column's wanted width after it closes, AppKit brought it back at 387–520 pt beside the 232 pt sidebar in a 1220 pt window whatever the maximum (1406 pt needed; about 4 runs of 10 of the `toggle` cases at 1200 and 1220 aborted), and a panel held at its maximum sprang to 520 the moment the sidebar hid. Moving the divider is what changes that width (lowering the closed column's maximum or its view's frame did not), so a panel that may come back wider than the room beside the sidebar in its window has its divider moved back to 310 just before it closes, by every path (`AppModel.normalizePanelBeforeClose`). As a fallback, `SplitViewTuning.panelRestoreBound` keeps the widest the column has shown since it was made or last narrowed that way (open or closed; the closed column's frame alone read 310, then 520 40 ms later), and opening a panel whose bound doesn't fit beside the sidebar hides it (`AppModel.fitInspector`). SwiftUI writes each presentation back through the inspector binding when its transaction ends (`true` about 250 ms after an open, `false` 300–400 ms after a close), and a panel reopened before the `false` of the close arrived was closed again by it (60 of 96 reopens 50–150 ms after a close). So a reopen within 1.5 s of a close waits until SwiftUI has written that close back and the sidebar it brings back is in (`AppModel.toggleInspector`, `reopenMustWait`), then opens; the binding's `false` reaches the model through `inspectorPresentationEnded`. Every user action goes through the model, so closes and ordinary opens never wait.

The sidebar and a panel share the window only when both fit. Otherwise the one asked for last wins, as in Music: opening a panel (counted at the width it comes back at) or narrowing the window hides the sidebar (narrowing keeps it down to 1112 pt on macOS 26, the sidebar at 190 beside the panel at 310; 922 on macOS 15), showing the sidebar closes a panel it doesn't fit beside, and closing a panel brings back a sidebar it hid. Showing the sidebar takes room for its 232 pt ideal width (`SplitViewTuning.sidebarIdealWidth`, which `SidebarMetrics.idealWidth` and the column use; SwiftUI brings it back at that width; with less room the sidebar's and the panel's caps chase each other) beside the panel's current width, at least 310: 1196 pt on macOS 26, 964 on macOS 15 (`SplitViewTuning.sidebarFitsBesidePanel`). The sidebar's search (`revealSearch`) follows the same rule. It never resizes the panel. Every way of showing the sidebar goes through `AppModel.showSidebarBesidePanel` before AppKit lays the column out: the toolbar's button and View › Show Sidebar (⌃⌘S, our own command in place of `SidebarCommands`, whose item AppKit applied directly) set `columnVisibility`, and anything that uncollapses the column in AppKit arrives through key-value observing of the sidebar's split view item.

While the sidebar's column animates in (from the moment that observation sees it uncollapse, for 0.8 s; the animation takes about 0.5 s), the main window can't get narrower than it was when the animation began (`SidebarAnimationGuard`, which exchanges `NSWindow.setFrame(_:display:)` and `setFrame(_:display:animate:)` once; live resizing goes through them too). Only intent counts as what the window should become (`ShrinkDeferral`): the user's live resize, a zoom, tile or script (their first caller outside OpenMusic is AppKit) and the app's own frames, which go through `NSWindow.requestFrame` (use it for every frame the app sets on the main window: app code can run under SwiftUI, in a `.task` or a button's action, and would look like SwiftUI's). A narrower intent is clamped to that width and applied when the guard ends; a wider one goes through at once and stays the window's size. SwiftUI's own frames (`NSHostingView.updateAnimatedWindowSize`, from `windowDidLayout`, told apart by their first caller outside OpenMusic) are never remembered and can't take the window below that width or below the latest intent: 150 ms into the animation SwiftUI set a window just widened to 1300 back to 960 and stepped it toward 955, which the guard used to apply at its end. With no intent the guard applies nothing at its end. A shrink to 900 pt mid-animation made SwiftUI grow the window by the width it lost, pass after pass, until AppKit aborted, although the columns fit 900. SwiftUI owns the window's delegate, so `windowWillResize` isn't an option. In native full screen the window can't grow, so showing the sidebar beside a panel where both fit is left to SwiftUI (the AppKit restore skips full screen and used to loop with the binding). After AppKit shows the sidebar and closes a panel, only a widening AppKit itself made is put back, and only if nothing has resized the window since (`WidthCorrection`: `setFrame` calls, live resize and full screen move its stamp). At launch the split view's autosave can restore the sidebar collapsed while `columnVisibility` starts at `.all`; the binding takes AppKit's state and the sidebar comes back through AppKit at the window's width (`adoptRestoredSidebar`), and the columns are fitted as soon as the window is watched. View › Show/Hide Sidebar is enabled only while the main window is open and key or main (`canToggleSidebar`); SwiftUI refreshes its menu items only as a menu opens (`menuNeedsUpdate`), so a test that reads or chooses one must call that first.

`scripts/mac.sh <slot> 'CONFIG=debug scripts/bundle.sh && scripts/mac-selftest.sh resize 3'` checks it: shrinking in steps, in one jump, during the open animation, after closing, the moment the sidebar starts to return (`guard`), by dragging the corner, with the widest columns, showing the sidebar with a panel open by each path at 1220 to 900 pt, widening right after AppKit showed the sidebar, at 150 and 350 ms, which must end at 1300 (`widen`), reopening at 1220 pt a panel dragged to 520 pt while the sidebar was hidden, the columns fitting whenever the sidebar shows (`reopen`, after a 1440 round trip; `rapid`, 0–400 ms after the close, the same panel or the other, which must be open 1 s after the reopen goes ahead), with a count of reopens that hid the sidebar although the panel fit beside it, showing it in native full screen (`fullscreen`), the menu item's enabled state (`menu`), and a relaunch with a narrow saved frame and lyrics open at once (`relaunch`, two launches). Each settled step must fit, keep the page's 420 pt, keep the window at the width it was given, and show the panel and sidebar the rule says. `OPENMUSIC_RESIZE_TRACE=1` logs the rule's decisions and the column caps. Any new minimum width inside the page or a column limit change goes into that arithmetic (`ColumnWidthTests` covers both OS versions). `scripts/mac-selftest.sh <name> [runs]` runs any mock self-test under the shared UI lock, which it holds from before the launch until no process carrying the run's marker argument is left, also when interrupted (^C, TERM to the script or its `--locked-run`; it signals the `--locked-run`, never `lockf`, which lets the lock go as soon as it is signalled) or when the process can't be found; it relaunches the app once when a self-test's last line is `RELAUNCH`, and reports AppKit's exception and crash report for a run that aborts (matched to that run's own app processes: a run's time span includes waiting for the lock while other runs' apps were up). `scripts/mac-selftest-check.sh` checks the lock and cleanup rules.

## Mac app: OpenMusic Sync

`Sources/OpenMusic/Sync/`. `AppModel.launch()` creates `SyncHub` once the providers restored their sessions (never with `OPENMUSIC_MOCK` or snapshots). It wires `SyncService` and `SyncCoordinator` to the one player, both sign-in transfers, `PlaybackSettings` and recent searches.
- **Account.** `SyncHub.account` (`AccountService`) loads the saved Clerk sign-in at launch; signed in, `connect()` registers the Mac (`SyncService.signIn`). Signed out, the account is met in the first-run flow's Sync step (`FirstRunFlow`, docs/onboarding.md); after Do This Later on its Approve step the hub keeps a quiet "Approve this Mac" banner in `model.playerBanner` until the key arrives (`approvalDeferred`). Switching servers signs out and `AppModel.restartSync()` makes a new hub.
- **Connection.** Opens only while signed in; it closes after Sign Out. Heartbeats run while OpenMusic is in use (active, or its window on screen with the display awake) or playing. Wake from sleep and network changes reconnect at once.
- **Links.** `openmusic://` arrives through `AppDelegate.application(_:open:)` into `URLRouter`. Only Debug self-test links (`openmusic://test/…`) act; the Clerk social sign-in callback (`openmusic://oauth-callback`) goes to the web authentication session.
- **UI.** The Devices popover is `DevicesButton` in `PlayerTrailing.destination` (full tier); the narrower tiers use `DevicesMenuSection` in "…". The banner is `model.playerBanner` with artwork and live position. Other entry points are Controls › Continue from <device> (⇧⌘C) and Controls › Play On, Settings › Account (`AccountSettingsPane`), the "Allow <device>…?" alert (an `NSAlert` sheet on the main window run by `SyncHub.keyPrompter`, `KeyRequestPrompter`: never SwiftUI's `.alert`, which crashed AppKit closing itself mid-layout when its request ended; it shows one exchange, closes when that exchange ends or the hub stops, and brings up the next; dismissals are per exchange, `DismissedKeyRequests`), and `SyncAwareSignOutButton` in Settings › Services. Sign-out runs `trySignOut()` first (its failure shows the alert), then `signIns.signOut(_:everywhere:)` on a registered Mac.
- **Live checks (debug builds only; release builds compile the self-test out).** Launch arguments: `-OpenMusicSyncSelfTest YES -OpenMusicSyncDir <dir> -OpenMusicSyncJWTFile <file> [-OpenMusicSyncState <file>] [-OpenMusicSyncDeviceName <name>]` (the JWT file holds a Clerk session token for a test user). They give a log and a command file of `openmusic://test/…` lines (`SyncSelfTest.swift`). `-OpenMusicSyncState` keeps the token in a file, not the shared Keychain. A self-test run also keeps every other Keychain account (YouTube Music and Spotify sign-ins included) in 0600 files under `-OpenMusicKeychainDir` (default `<OpenMusicSyncDir>/keychain`), so it never restores, changes or uploads the Mac's real sign-ins; `scripts/keychain-snapshot.sh` (attributes only), run before and after, shows the login Keychain's OpenMusic items unchanged. `scripts/e2e-sync.sh` is the live accounts check of both apps against the dev deployment ([docs/maintainers.md](docs/maintainers.md#live-sync-check)).

## Mac app: playlists, selection and the sidebar

These rules are also what the review screenshots check ([docs/maintainers.md](docs/maintainers.md#review-screenshots), where each capture's checks are listed).

Playlist pages (`PlaylistPager`, `PlaylistContent`): a playlist whose service gave a total of up to 200 songs loads its later pages when opened, at most `eagerPageBudget` pages, and a token handed out twice ends the list; fresh detail replaces the pager, cancelling its request, and the new pager loads back to the length the old one had while the rows hold their selection (`PlaylistContent.Refill`, `TrackListView.holdsSelection`): a failed page keeps the target and the hold, Try Again goes on refilling, and the hold ends only on catching up or at the list's real end; the refill asks for at most the old pager's pages plus 2 (20 at most) by itself, then goes on as the listener scrolls, still holding, and no eager page loads while it holds (`PlaylistContent.nextLoad`). The track list stays mounted when Find matches nothing ("No songs match" shows above it) and while a page with no rows to show (a first page of only local files or episodes) still has pages after it; it loads those by itself up to `PlaylistPager.emptyPageBudget` (5 pages, counted as eager pages too, and none while a refill holds past its budget), then shows Load More with the list and any held selection kept; "This playlist is empty" shows only once the end is known and no refill holds (`PlaylistContent.showsEmptyState`), so a held selection survives; Find and the sort stay while either is in use, and one sort orders the rows and what Play queues. `PlaylistPageHostTests` checks it on the real page in an `NSHostingView`, selecting a later page's row through `PlaylistPageProbe` (Debug only, in the environment), with a page that fails; YouTube's parser leaves `trackCount` nil rather than passing the first page's length off as the total; every request is awaited in the page's `.task`, so leaving the page cancels it; `PlaylistPagerTests`.

Album and playlist track lists select several rows as a Mac table does (`TrackSelection`, keyed by `Track.id`). A playlist lists each song once, with a multiplicity marker: a song it holds twice keeps its first place and its row says "2×" (3×…) in the readable secondary ink just before its time, read by VoiceOver as "in this playlist twice" (`CopiesMarker`, `PlaylistPager.copies`); a copy on a later page adds to the row listed earlier, never dropped. The header always gives the service's total of entries (`PlaylistPager.entryTotal`; the rows' copies add up to it), never the number of rows, and the total length counts every copy; a list cut short by a token handed out twice is not complete (no length), and neither is one with entries OpenMusic leaves out (Spotify's local files and episodes: their lengths are unknown, `songCountLine`). What plays or is queued from it takes each song once (`AppModel.eachOnce`). Remove from Playlist takes the song out entirely, every copy, on both services (Spotify removes by URI; YouTube reads the playlist's entries and removes each `setVideoId` of the song, `YouTubeMusicProvider.removalEdits`, and refuses before writing, with a notice, when a copy has no `setVideoId`); its menu item names the copies ("Remove Both Copies", "Remove All 3 Copies", a selection's copies in all; `TrackMenu.removeTitle`), and the confirmation ("Remove both copies of “X” from “P”?", counted before it shows, `PendingPlaylistRemoval.entries`) or the notice with Undo ("Removed all 3 copies of “X”…") says so, and Undo puts every copy back at its place. Places are the service's own entry numbers (`Page.positions`/`PlaylistDetail.positions`: Spotify's local files and episodes, left out of the rows, still hold a place). Playlist edits go one at a time per playlist, and each listener action is one record (`PlaylistEdit`, `Sources/OpenMusic/App/PlaylistEdit.swift`). A playlist's state lives in the model, never in a notice (`AppModel.playlistEdits`, `PlaylistEditState`): idle, in flight (a removal reading its places or sending requests, Try Again, Undo, an add or a drop), or partly applied (a run stopped after the service acknowledged some requests). While it isn't idle the playlist takes no other edit: Remove and Add to Playlist for it are disabled (`AppModel.canEdit`), and a removal, add or drop is refused (`refusesEdit`: "Finishing the last change to “P”…" while in flight; for a partly applied edit its failure notice comes back). A partly applied edit stays locked until Try Again finishes it, its Undo puts back what the service acknowledged, or the listener picks Leave As Is (the notice's last button, `Notice.secondaryAction`), which ends it and keeps the playlist as the service has it, with no Undo. Closing or replacing the notice never unlocks; with its notice closed the playlist page shows the same three buttons in a banner over the list (`PartialEditBanner`). A removal that fails before anything went leaves the playlist idle, and its Try Again is a new removal. Other playlists are unaffected. The record reads the songs' places once, then tracks exactly what the service acknowledged, request by request (`playlistEditBatchSize`, Spotify 100): which songs are out, which places are empty. Try Again goes on toward the same goal; Undo fills only places acknowledged empty (in place order, so each lands at its entry number). Undo is single-level, and nothing replaces NSUndoManager's methods: a removal goes on the window's undo manager only once every request was acknowledged, in an undo group of its own at the top level, registered with its service's dedicated target (`PlaylistUndoTarget`, one per service). Inside another component's open group (`groupingLevel > 0`; with event grouping, anything registered earlier in the same run-loop pass) the registration waits for a later turn (`RunLoop.main.perform` in the default, event-tracking and modal modes, then every 50 ms, about 10 s at most, after which only the notice offers Undo) and never closes anyone else's group; at the top level event grouping is off for that one registration, since `beginUndoGrouping` at level 0 would otherwise open the pass's event group around it and a queue action later in the same pass would share its ⌘Z (`registerUndoAtTopLevel`). A newer edit or the notice's Undo cancels a registration still waiting (`undoRegistrations`); starting any playlist edit (or settling one) first takes the earlier one off with `removeAllActions(withTarget:)` and drops its notice (`purgePlaylistUndo`), so at most one playlist edit is in history and its places are always current. The queue's and text fields' actions stay. Edit › Undo (⌘Z, when it is on top) and the notice's Undo run the same put-back once: the menu's pops the action and replaces the notice, the notice's removes the action from the manager. There is no Redo for playlist edits: undoing registers nothing (removing again is one click), so the Edit menu never offers "Redo Remove…". Handlers hold the record and capture the model weakly, never the manager. Every read an edit makes (the removal's places, every put-back's check, Add Back at End) goes through `MusicProvider.uncachedPlaylist`/`uncachedPlaylistTracks`, which neither read nor write a cache: not the API's own (Spotify caches playlist GETs for 60 s; its `fresh:` reads skip it, so a cached read's late response can't stand in for one), and not the HTTP cache either (`HTTP.session` has a `URLCache` and `.useProtocolCachePolicy`; uncached requests carry `.reloadIgnoringLocalAndRemoteCacheData` and go through `HTTP.uncachedSession`, an ephemeral session with no `URLCache`, via `SpotifyTransport.send(_:uncached:)`; YouTube's client session already has none). What cache headers Spotify sends on playlist reads hasn't been checked: nothing logs response headers. every page up to `editReadPageLimit` (200), checking cancellation and that the service still sends as the edit's account before and after each page; a continuation handed out twice ends the read as incomplete. Every put-back (Edit › Undo, the notice's or the banner's Undo, and a put-back's Try Again) first reads the playlist again and compares it with the entries the record read before its first request less what the service acknowledged (`PlaylistEdit.expectedEntries`: ordered song ids with YouTube's `setVideoId`; entries left out of the pages with the identity the service gives them, `Page.unlistedEntries`: Spotify's `spotify:local:` and episode URIs; a place put back matches its song under any entry id). Only an identical, complete list in which every entry on both reads is identified (`isUnchanged`) gets songs back at their places: a `null` entry could have moved unseen, so a playlist holding one always takes the changed-playlist path. Otherwise the playlist changed outside OpenMusic (another device, the service's app): nothing is inserted, the edit ends unlocked with no Undo, the open page reloads, and the notice says "“P” changed since you removed this song." (these songs) with Add Back at End (appends the songs still out, each once, skipping any the playlist holds again, read once more at the click and only from a complete read: an incomplete one appends nothing and says "Couldn’t read all of “P”." with Try Again, which reads again, so a Try Again after an append that stopped partway never adds a song twice) and Cancel. A read that fails counts as a failed put-back request (partly applied, Try Again). Spotify's `snapshot_id` isn't used: the snapshot after our own last write can already include another device's change made between our requests, so equal snapshots wouldn't prove the places current; the entry comparison is the check. No read can rule out a write landing between the check and the insert: without the service checking a version on the write itself, a concurrent change in that window can still shift a place. Each edit belongs to the account it began under (`PlaylistEditAccount`: the service and its immutable account id; without an id, the exact `ProviderSession`), not to the token: a refresh or a sign-in synced from another device for the same account keeps the edit and its Undo. Before every request the service must send as that account with no swap under way (`canSend`, which needs a current `.account` session in both of its branches; a swap in progress, `.changing`, stops the run with "Your Spotify sign-in was changing." and Try Again, nothing sent), and after every wait a run whose account the service no longer holds stops silently. That main-actor check isn't enough on its own: the write crosses into `@concurrent` service code and the API actor, where a synced sign-in can install another account's token first. So every playlist write (remove, insert, append, Add to Playlist, New Playlist and its songs) goes through the bound calls `MusicProvider.add/remove/insert/createPlaylist(…, as: PlaylistWriteAccount)`: the provider checks the account on the main actor and turns it into a binding (Spotify: `SpotifyWriteBinding`, the user id, or without one the provider's token-swap epoch; YouTube: `YTMWriteBinding`, the datasync account id or the credential-swap epoch), and the network actor checks it again where it picks the credentials, for every chunk, retry and attempt, with nothing suspending between that check and the send (`SpotifyAPI.data`, `InnerTubeClient.post`/`checkWriteBinding`). A mismatch sends nothing and throws `PlaylistEditError.accountChanged` (the same "sign-in was changing" notice with Try Again). A new token for the same user still writes (a bound Spotify write whose session moved to the same user's new token goes again with it); before a bound Spotify write the API learns whose token it holds from `/me` if it doesn't know. No edit starts during a swap: `beginPlaylistEdit` refuses with that notice and Try Again, and the confirmation's count and New Playlist do too. New Playlist keeps the playlist once the service acknowledged it: if adding its songs fails, Try Again adds them to that playlist (`fillNewPlaylist`), never making a second one (`NewPlaylistBindingTests`). The songs go in requests of the service's batch size and the record (`NewPlaylistFill`) keeps what each acknowledged, so Try Again sends only what is pending; after a failure that may have landed anyway (`writeMayHaveLanded`: a timeout or a 5xx, not offline, 429, 401 or an account refusal) it first reads the playlist uncached and whole and sends only the pending songs it doesn't hold, as Add Back at End (`NewPlaylistFillTests`). Recovery actions (Add Back at End and its Try Again, Try Again, Undo) keep the original edit's account and never take the current one. When the service signs out or holds another account, `dropEditsOfChangedAccounts` cancels that service's runs in flight and a confirmation's count of copies (`confirmationRead`), releases their locks and partly applied edits, takes their Undo off (`removeAllActions(withTarget:)` on the service's target), and drops their notices (`Notice.account`), a changed playlist's Add Back at End and a pending removal's confirmation. The page's banner (`PartialEditBannerSlot`) sits outside the list: over the rows, over "This playlist is empty" when the edit took the last song, and over the page's load error (`Loadable.failureHeader`); `PlaylistPageProbe.editBanner` is set by the mounted banner itself. `PlaylistWriteBindingTests` (another account's credentials landing before an Undo's insert, a removal's or an add's request; a same-account token mid-edit; an edit asked for and Add Back at End clicked during a swap), SpotifyKit's and YouTubeMusicKit's `WriteBindingTests` (the network-side check, the uncached session and request policy), `PlaylistUndoConservativeTests` (a swap of unidentified and of identified left-out entries, uncached reads, a same-user and a different-user transfer, no write while the sign-in changes, Add Back at End and its Try Again after a partial append only from a complete read, a confirmation's count stopping on an account switch), `PlaylistUndoSafetyTests` (drift by an insert, by an external re-add, none, and on a partial put-back's Try Again; Cancel; an account switch mid-batch, Undo and Try Again after a switch, sign-out; the deferred top-level registration with a queue action in the same turn), `PlaylistUndoTests` (a reviewer's P1 sequence, purging, the two entry points, the lock, queue and text-field Undo beside a playlist edit, no Redo), `PlaylistEditTests` (batch size 2, `MockProvider.playlistEditGate` holds a request in flight) and `PartialPlaylistEditTests` (Leave As Is) cover it with `MockProvider.editBatchSize`, `playlistEditFailures` and `unlistedTrackIDs`;

Selection: ⌘-click, ⇧-click from the anchor, ⇧↑/⇧↓, ⌘A (Edit › Select All through `onCommand`, else the key), Escape; a selected row's context menu and More then act on the selection in the order shown (`TracksMenu`: Play Next, Add to Queue, Add to Playlist, Remove from Playlist as one removal with one Undo), and neighbouring selected rows join into one fill. Removing the anchor or lead elsewhere moves it to the nearest selected row still there: inside the old range first, else the selected row closest to where the anchor sat in the previous order (A, ⌘G, ⌘H, H removed: G) (`TrackSelection.keep(_:previous:)`), so ⇧-click and ⇧↑/⇧↓ keep extending. A row's More rests in the quiet `readableSecondary` gray, the label color under the pointer or on the unfocused selection, white on the focused one (`MoreButtonInk`, palette symbol images, since AppKit ignores the foreground style around a pull-down menu's label).

Playlists and Recently Played leave out each service's own liked-songs playlist (`Playlist.isLikedSongs`: YouTube's Liked Music, Spotify's Liked Songs; All Playlists keeps them), so Library › Liked Songs, whose heart turns into a play button on hover or focus (an accent disc with a white Play, Pause or spinner in the 20 pt slot, darker while pressed; `sidebar-hover-crop` logs its fill) (`AppModel.playLikedSongs`, context `likedSongsContext`), is the one liked entry (on Home it stands in for the service's liked playlist as a card; with two services signed in the card plays both, so its shelf's header names no service and the shelf's other cards carry their own marks, `ShelfView.mixesServices`); `sidebar-selected` logs that as `liked entries` (PASS/FAIL). Recently Played also leaves out what already has a row above it (pinned, or one of the service's playlists), and a playlist page highlights one row: Pinned if pinned, else Playlists (`AppModel.canonicalSidebarSelection`); `sidebar-selected` logs a `sidebar selection` PASS/FAIL line per way in.

Search: each query and scope gets its own results page (`.id(key)` in `SearchResultsView`), so a switch never keeps another scope's offset. The Songs table's Service column shows only while the list mixes services (`SongsTable.showsServiceColumn`, judged on the whole list, not Find's matches). Lyrics panel: the panel's top fade is 46 pt (a line and its spacing) once the list has scrolled and 20 pt at rest, ending above the first line (`LyricsStyle.panelTopFade`, `PanelTopFadeMask`, switched by a Bool from `onScrollGeometryChange`, never per frame, with hysteresis: on past 4 pt, off under 1 pt, `TopFadeBand`).
