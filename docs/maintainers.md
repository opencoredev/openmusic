# Maintainer tooling

Optional tooling the maintainers use: building the Apple apps on a Mac over SSH from a Linux checkout, installing on their own devices, deploying the hosted sync backend, running the Windows app in a VM, and making screenshots. None of it is needed to build, test or contribute: [CONTRIBUTING.md](../CONTRIBUTING.md) covers that on your own machine.

## What it depends on that isn't in the repository

- `scripts/local.env` (gitignored; copy `scripts/local.env.example`): SSH targets and signing values. `scripts/env.sh` reads it; a variable already set in the environment wins, and every script names any variable it needs that is unset.
- A **build Mac** reachable over SSH with key login (`OPENMUSIC_MAC_HOST`): Xcode 27, XcodeGen and, for the README images, `cwebp` (`brew install webp`).
- For iPhone installs, a **device Mac** the iPhone is paired with (`OPENMUSIC_DEVICE_HOST`), holding an Apple Development identity and an Xcode-managed wildcard provisioning profile (`OPENMUSIC_DEV_IDENTITY`, `OPENMUSIC_TEAM_ID`, `OPENMUSIC_PROFILE_UUID`, `OPENMUSIC_IPHONE_UDID`).
- For deployments, a machine where the **Convex CLI** is logged in to the project, with `~/agents/openmusic-sync/.env.local` (`OPENMUSIC_CONVEX_HOST`, or `local`).
- For live sync checks, the hosted **Clerk** instance's secret key and test users, kept in 0600 files outside the repository (below).
- For the Windows app from Linux, a **Windows 11 VM** with the .NET 10 SDK and OpenSSH, and a helper script that drives it (`OPENMUSIC_WIN_VM`); neither is in the repository.
- `scripts/check-public.sh` reads a gitignored `scripts/private-patterns.txt` (one extended regex per line) and fails on any tracked line that matches; without the file it passes.

## Build Mac

The checkout can live on Linux or a Mac. `scripts/mac.sh <slot> '<command>'` rsyncs the checkout to `~/agents/openmusic-<slot>` on the build Mac and runs the command there in a bash login shell. Use your own slot name, and remove the slot folder when you are done.

```bash
scripts/mac.sh <slot> 'swift build'
scripts/mac.sh <slot> 'swift test'
scripts/mac.sh <slot> 'swift run openmusic-probe ytm search "<query>"'
scripts/mac.sh <slot> 'scripts/bundle.sh'        # build/OpenMusic.app, signed with the local identity
```

The build Mac may be shared: keep jobs bounded, run UI captures under the shared lock (`lockf /tmp/medley-ui.lock`, which the capture scripts take themselves), and wait for the load to drop before comparing timing runs. Its speakers may be muted, so check playback through player state.

iPhone app on the build Mac's simulators:

```bash
scripts/ios.sh <slot> build                                          # xcodegen + xcodebuild
scripts/ios.sh <slot> run                                            # build, install, launch (live YouTube Music)
scripts/ios.sh <slot> run -OpenMusicMock YES -OpenMusicScreen album  # sample data, opens one screen
scripts/ios.sh <slot> snapshots                                      # every screen, light and dark, into build/shots/
scripts/ios.sh <slot> selftest                                       # live check: home, search, album, play, lyrics, backgrounding
scripts/ios.sh <slot> perf                                           # frame timing (AGENTS.md, iOS app: frame timing)
scripts/ios.sh <slot> delete                                         # delete the slot's simulator
```

## Installing on the maintainers' devices

A real iPhone is installed from the Mac it is paired with (`OPENMUSIC_DEVICE_HOST`), which holds an Apple Development identity; the build Mac needs no Apple ID. `scripts/install-iphone.sh <password-file>` runs the whole recipe; its device-Mac half, `scripts/iphone-sign.sh`, unlocks the keychain from stdin and signs in one SSH command. Recipe: rsync the repo to `~/agents/openmusic-device`, `xcodegen`, then `xcodebuild -configuration Release -destination generic/platform=iOS CODE_SIGNING_ALLOWED=NO`; copy an Xcode-managed wildcard profile (`OPENMUSIC_PROFILE_UUID`, team `OPENMUSIC_TEAM_ID`) in as `embedded.mobileprovision`, `codesign` with the `OPENMUSIC_DEV_IDENTITY` identity and entitlements `application-identifier <team>.dev.openmusic.OpenMusicMobile`, `com.apple.developer.team-identifier`, `get-task-allow`, `keychain-access-groups`; `xcrun devicectl device install app --device <OPENMUSIC_IPHONE_UDID>`. Over SSH the login keychain is locked (errSecInternalComponent): the script unlocks it with that Mac's login password, read from a file piped over ssh stdin (never in a command's arguments) and deleted afterwards. Manual signing with the managed profile is refused by xcodebuild, and automatic signing would register a new App ID on the team, so don't use either.

`scripts/install-macbook.sh` makes a release `scripts/bundle.sh` build on the build Mac (it has the signing identity) and installs it with `ditto` in `/Applications/OpenMusic.app` on the device Mac. Never install an ad-hoc or debug build as the copy someone uses day to day.

## Live sync check

`scripts/e2e-sync.sh` (after `scripts/ios.sh <slot> build`; run it as `scripts/mac.sh <slot> 'OPENMUSIC_SLOT=<slot> scripts/e2e-sync.sh'`) is the live accounts check against dev and the real Clerk instance, under the shared UI lock: both apps sign in through the real sign-in sheet (the email and the code typed with the self-test's `type`), register, see each other, run the six-digit exchange both ways (`allow`/`deny` press the Mac alert's own buttons, `askagain` and `codes-match` on the new device, the codes compared from both logs, the alert checked on screen through `PRESENTED` lines), hand playback off, and carry a test sign-in through the vault; PASS/FAIL lines in `build/e2e/results.txt`, timings in `timings.txt`, light and dark captures of the welcome, sign-in sheet, Settings › Account and the Allow alert in `shots/`. It reads the test user's email from `~/.config/openmusic/clerk-test-email` on the build Mac (0600), erases its own slot's simulator first (a reused one stopped loading YouTube streams after the fake sign-in), removes devices an interrupted run left on the account (`remove-others`), and signs both apps out on any exit.

## Windows VM

`scripts/windows-vm.sh` wraps the VM helper (`OPENMUSIC_WIN_VM` in `scripts/local.env`, default `~/vms/medley-win/win.sh`). The helper takes `push <dir> <slot>`, `ps <powershell>`, `gui <slot> <command line>`, `kill <process>`, `shot <out.png>` and `pull <remote glob> <dir>` against a Windows 11 VM with the .NET 10 SDK and OpenSSH:

```bash
scripts/windows-vm.sh build              # push windows/ to the VM and build (Debug, x64)
scripts/windows-vm.sh publish            # Release, self-contained
scripts/package-windows.sh               # publish, then the release zip: build/OpenMusic-<version>-windows-x64.zip
scripts/windows-vm.sh run --play         # start it in the VM's desktop session
scripts/windows-vm.sh shot out.png       # screenshot the VM screen
scripts/windows-vm.sh snapshot out/      # --snapshot in the VM, PNGs copied to out/
scripts/windows-vm.sh log                # tail the app log
```

Set `OPENMUSIC_VM_SLOT` to use your own slot. The script touches pushed files after copying because the VM sees the host's mtimes as older than its build output, which made incremental builds skip changes. `scripts/windows-selftest.sh launch '<args>' -- '<command>' …` runs the Debug self-test steps one by one (`snap`, `log` and any `Services/SelfTest.cs` command); `scripts/windows-uia.ps1` clicks and types by AutomationId in the VM's desktop session.

Every Windows release zip comes from `scripts/package-windows.sh` (`--no-publish` reuses the slot's last publish): it extracts to one `OpenMusic/` folder holding the publish, `LICENSE` and `THIRD-PARTY-NOTICES.txt`. The notices are written from the license and notice files of every package the publish contains (`windows/scripts/collect-notices.ps1` in the VM, then `scripts/windows-notices.py`), and packaging stops if a published file can't be traced to OpenMusic or to one of those packages, so a new dependency can't ship without its notice. CI's Windows job builds the same layout as an artifact.

Notes from setting up the VM:

- Without an audio device, MediaPlayer fails every source with `SourceNotSupported`. Give QEMU a virtual Intel HDA card with a `none` backend (output discarded): Windows gets a "Speakers" endpoint and playback runs. Check playback through the log's position lines.
- The VM has no GPU, so Mica draws its fallback color and every surface is in system memory (WARP).
- `win.sh gui` takes the command line unquoted: `win.sh gui win 'C:\path\OpenMusic.exe --play'`. Quoting the path inside breaks the scheduled task's command.

Places are the service's own entry numbers (`Page.positions`/`PlaylistDetail.positions`: Spotify's local files and episodes, left out of the rows, still hold a place). Playlist edits go one at a time per playlist, and each listener action is one record (`PlaylistEdit`, `Sources/OpenMusic/App/PlaylistEdit.swift`). A playlist's state lives in the model, never in a notice (`AppModel.playlistEdits`, `PlaylistEditState`): idle, in flight (a removal reading its places or sending requests, Try Again, Undo, an add or a drop), or partly applied (a run stopped after the service acknowledged some requests). While it isn't idle the playlist takes no other edit: Remove and Add to Playlist for it are disabled (`AppModel.canEdit`), and a removal, add or drop is refused (`refusesEdit`: "Finishing the last change to “P”…" while in flight; for a partly applied edit its failure notice comes back). A partly applied edit stays locked until Try Again finishes it, its Undo puts back what the service acknowledged, or the listener picks Leave As Is (the notice's last button, `Notice.secondaryAction`), which ends it and keeps the playlist as the service has it, with no Undo. Closing or replacing the notice never unlocks; with its notice closed the playlist page shows the same three buttons in a banner over the list (`PartialEditBanner`). A removal that fails before anything went leaves the playlist idle, and its Try Again is a new removal. Other playlists are unaffected. The record reads the songs' places once, then tracks exactly what the service acknowledged, request by request (`playlistEditBatchSize`, Spotify 100): which songs are out, which places are empty. Try Again goes on toward the same goal; Undo fills only places acknowledged empty (in place order, so each lands at its entry number). Undo is single-level, and nothing replaces NSUndoManager's methods: a removal goes on the window's undo manager only once every request was acknowledged, in an undo group of its own at the top level, registered with its service's dedicated target (`PlaylistUndoTarget`, one per service). Inside another component's open group (`groupingLevel > 0`; with event grouping, anything registered earlier in the same run-loop pass) the registration waits for a later turn (`RunLoop.main.perform` in the default, event-tracking and modal modes, then every 50 ms, about 10 s at most, after which only the notice offers Undo) and never closes anyone else's group; at the top level event grouping is off for that one registration, since `beginUndoGrouping` at level 0 would otherwise open the pass's event group around it and a queue action later in the same pass would share its ⌘Z (`registerUndoAtTopLevel`). A newer edit or the notice's Undo cancels a registration still waiting (`undoRegistrations`); starting any playlist edit (or settling one) first takes the earlier one off with `removeAllActions(withTarget:)` and drops its notice (`purgePlaylistUndo`), so at most one playlist edit is in history and its places are always current. The queue's and text fields' actions stay. Edit › Undo (⌘Z, when it is on top) and the notice's Undo run the same put-back once: the menu's pops the action and replaces the notice, the notice's removes the action from the manager. There is no Redo for playlist edits: undoing registers nothing (removing again is one click), so the Edit menu never offers "Redo Remove…". Handlers hold the record and capture the model weakly, never the manager. Every read an edit makes (the removal's places, every put-back's check, Add Back at End) goes through `MusicProvider.uncachedPlaylist`/`uncachedPlaylistTracks`, which neither read nor write a cache: not the API's own (Spotify caches playlist GETs for 60 s; its `fresh:` reads skip it, so a cached read's late response can't stand in for one), and not the HTTP cache either (`HTTP.session` has a `URLCache` and `.useProtocolCachePolicy`; uncached requests carry `.reloadIgnoringLocalAndRemoteCacheData` and go through `HTTP.uncachedSession`, an ephemeral session with no `URLCache`, via `SpotifyTransport.send(_:uncached:)`; YouTube's client session already has none). What cache headers Spotify sends on playlist reads hasn't been checked: nothing logs response headers. every page up to `editReadPageLimit` (200), checking cancellation and that the service still sends as the edit's account before and after each page; a continuation handed out twice ends the read as incomplete. Every put-back (Edit › Undo, the notice's or the banner's Undo, and a put-back's Try Again) first reads the playlist again and compares it with the entries the record read before its first request less what the service acknowledged (`PlaylistEdit.expectedEntries`: ordered song ids with YouTube's `setVideoId`; entries left out of the pages with the identity the service gives them, `Page.unlistedEntries`: Spotify's `spotify:local:` and episode URIs; a place put back matches its song under any entry id). Only an identical, complete list in which every entry on both reads is identified (`isUnchanged`) gets songs back at their places: a `null` entry could have moved unseen, so a playlist holding one always takes the changed-playlist path. Otherwise the playlist changed outside OpenMusic (another device, the service's app): nothing is inserted, the edit ends unlocked with no Undo, the open page reloads, and the notice says "“P” changed since you removed this song." (these songs) with Add Back at End (appends the songs still out, each once, skipping any the playlist holds again, read once more at the click and only from a complete read: an incomplete one appends nothing and says "Couldn’t read all of “P”." with Try Again, which reads again, so a Try Again after an append that stopped partway never adds a song twice) and Cancel. A read that fails counts as a failed put-back request (partly applied, Try Again). Spotify's `snapshot_id` isn't used: the snapshot after our own last write can already include another device's change made between our requests, so equal snapshots wouldn't prove the places current; the entry comparison is the check. No read can rule out a write landing between the check and the insert: without the service checking a version on the write itself, a concurrent change in that window can still shift a place. Each edit belongs to the account it began under (`PlaylistEditAccount`: the service and its immutable account id; without an id, the exact `ProviderSession`), not to the token: a refresh or a sign-in synced from another device for the same account keeps the edit and its Undo. Before every request the service must send as that account with no swap under way (`canSend`, which needs a current `.account` session in both of its branches; a swap in progress, `.changing`, stops the run with "Your Spotify sign-in was changing." and Try Again, nothing sent), and after every wait a run whose account the service no longer holds stops silently. That main-actor check isn't enough on its own: the write crosses into `@concurrent` service code and the API actor, where a synced sign-in can install another account's token first. So every playlist write (remove, insert, append, Add to Playlist, New Playlist and its songs) goes through the bound calls `MusicProvider.add/remove/insert/createPlaylist(…, as: PlaylistWriteAccount)`: the provider checks the account on the main actor and turns it into a binding (Spotify: `SpotifyWriteBinding`, the user id, or without one the provider's token-swap epoch; YouTube: `YTMWriteBinding`, the datasync account id or the credential-swap epoch), and the network actor checks it again where it picks the credentials, for every chunk, retry and attempt, with nothing suspending between that check and the send (`SpotifyAPI.data`, `InnerTubeClient.post`/`checkWriteBinding`). A mismatch sends nothing and throws `PlaylistEditError.accountChanged` (the same "sign-in was changing" notice with Try Again). A new token for the same user still writes (a bound Spotify write whose session moved to the same user's new token goes again with it); before a bound Spotify write the API learns whose token it holds from `/me` if it doesn't know. No edit starts during a swap: `beginPlaylistEdit` refuses with that notice and Try Again, and the confirmation's count and New Playlist do too. New Playlist keeps the playlist once the service acknowledged it: if adding its songs fails, Try Again adds them to that playlist (`fillNewPlaylist`), never making a second one (`NewPlaylistBindingTests`). ### First-run flow

`scripts/onboarding-shots-apple.sh <dir> [mac|ios|both]` (from a Linux checkout; it needs a Clerk helper script that creates and deletes test users, kept outside the repository) makes two Clerk test users, runs both apps from a fresh install through every step of the [first-run flow](onboarding.md) live against the dev deployment, with `openmusic-probe` as the account's other devices (the holder that approves, a device asking this one, the device playing for the Continue banner), and writes the captures (light and dark, the Mac at 1200 x 780 and its 900 x 560 minimum, iPhone 17 Pro, the largest accessibility text size, an SE-sized screen) and PASS/FAIL lines to `<dir>`. It deletes the users afterwards. The apps are driven through their sync self-test command files: `firstrun?do=…` presses the flow's buttons, `firstrun?step=`, `server=`, `email=`, `code=` fill it in, and `firstrun?preview=youtubeMusic:Name,spotify:Name` (Debug only) shows the signed-in rows without a sign-in that would have to work against the real services. `key?k=tab|return|escape|cmd-[` and `window?w=&h=` are Mac only.
