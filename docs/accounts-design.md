# OpenMusic accounts: design

OpenMusic stops pairing devices with QR codes and invite codes. You sign in with Clerk on each device, and every device signed in to the same Clerk user syncs: playback handoff, remote control, settings and recent searches. YouTube Music and Spotify sign-ins still sync end-to-end encrypted, and so does everything about what you listen to and search for (`docs/sync-design.md`, "What the server can see"), so neither the hosted server nor its operator can read them.

This page is the plan. `docs/sync-design.md` stays the contract for everything that doesn't change (playback, commands, vault revisions, settings), and gets updated where this replaces it. Self-hosting is in `docs/self-hosting.md`.

## What the listener sees

1. **Welcome.** A first-launch screen with the app's name, one line about what it does, a **Sign In** button and a small **Use your own server** link. **Not Now** closes it; OpenMusic works without an account, as it does today, and Settings › Account offers Sign In later.
2. **Sign In.** A sheet with "Continue with Google" and "Continue with Apple" (when the Clerk app enables them) and an email field. Email: OpenMusic sends a 6-digit code, you type it, done. A new email address creates the account with the same two steps; there is no separate sign-up.
3. **Done.** The device registers itself and appears on your other devices within a second. It sees where the others play ("Playing on Riley's Mac · 2:13") and can control them at once; the songs, handoff and settings follow once it has the sign-in key (step 4).
4. **Sign-ins (YouTube Music, Spotify).** On a second device, Settings › Account says "Waiting for your other device" until a device that has your sign-ins (Riley's Mac) is open. Then both show the same six-digit code: the Mac asks "Allow Riley's iPhone to use your YouTube Music and Spotify sign-ins? Code 482 913", and the iPhone shows "Compare the codes · 482 913" with **Codes Match** and **Codes Don't Match**. You tap **Allow** on the Mac and **Codes Match** on the iPhone, in either order; the iPhone is signed in to both services a moment later. Closing the alert leaves an **Allow…** button on that device's row in Settings › Account. **Don't Allow** or **Codes Don't Match** ends the attempt; **Ask Again** starts a new one with a new code. Remote control and where each device plays work from step 3 on; what plays, handoff and settings wait for this, because they are sealed with the same key. If no device is around to approve, you sign in to YouTube Music or Spotify on the new device as usual.
5. **Settings › Account** shows who is signed in (name and email from Clerk), the server (OpenMusic, or the custom URL), your devices (rename, remove), and **Sign Out**. Signing out removes this device from your devices and deletes its sync data (the device token, its key pair and the vault key). Your YouTube Music and Spotify sign-ins on this device stay; Settings › Services (formerly Accounts) still offers "sign out on this device / on all devices" for those.
6. **Advanced › Custom server.** "Use your own server" (welcome screen) and Settings › Account › Server take one URL, for example `https://happy-otter-123.convex.cloud` or a self-hosted Convex URL. OpenMusic asks that server for its Clerk publishable key, then signs in against that server's Clerk app. Switching servers signs this device out of the old one.

A device removed on another device (Settings › Account › Devices › Remove) signs itself out the next time it hears from the server.

## How it works

### Identity

- Convex's Clerk integration: `sync/convex/auth.config.ts` names the Clerk issuer (`CLERK_JWT_ISSUER_DOMAIN`, application id `convex`). Every function except `config:get` calls `ctx.auth.getUserIdentity()`; without an identity it throws `unauthenticated`.
- The user is `identity.tokenIdentifier` (issuer plus subject). It is unique across Clerk apps, so a self-hosted server pointed at a different Clerk app can never mix users up. The server stores no email, name or other profile data; the apps read those from Clerk directly.
- A **library** stays the internal name for one user's sync group: `libraries.owner` is the token identifier, one library per user, created on the user's first device registration. Playback, queues, commands, vault and settings stay scoped by `libraryId`, so their functions don't change.

### Devices

- Each installation keeps a random 32-byte **device token**, generated on the device when it signs in, and an X25519 **device key pair** (CryptoKit `Curve25519.KeyAgreement`). Both live in the Keychain inside `sync.credentials` (no new Keychain account, so the Mac's Keychain service needs no change).
- `account:register({ token, device, publicKey, keyId? })` runs once after sign-in, and again at launch until it has succeeded. A device the server no longer knows never registers again on its own (see Removal), and the server enforces it: a device token is single-use for its lifetime (below). It finds or creates the user's library and upserts the device by the token's SHA-256, so a retry returns the same device. It returns `{ deviceId, libraryId, keyId, keyState }`. `keyId` is the fingerprint of a fresh key the device just made; only a library without a key adopts it (the first device). In a library that has a key, every new device starts as `requested`, whatever it sends: the fingerprint is visible to every device, so knowing it proves nothing.
- The device token doubles as the registration's request id. Before `account:register` is sent, the device saves what it will send (the token, its key pair and the proposed key, with the Clerk user and server it is for) as `sync.credentials.state.registration.v1`, inside the existing Keychain family; a registration that can't be saved isn't sent. Until the server answers, every attempt (a retry this session, or the next launch) sends the same registration, and the server answers a known token with the same device and its key state, before the rate limit and without counting toward it. So a first device whose answer was lost (a timeout, or the app quit) still gets the account's first key and the token of the device that holds it, instead of leaving a holder row nobody can use, which would block claims until that device was evicted or the account expired. The answer settles it: holding the proposed key, the device adopts it; named with another key or as asking, it drops the proposal and asks like any other device; refused (`unauthorized`: the token names a device of another account or a retired library; `invalidArgument`), it never landed, and the next attempt starts with a new token and key. The saved registration is dropped once the credentials are saved, and also on sign-out or for another user or server. When the credential store refuses the credentials, the device still syncs from memory, but `signIn` throws ("couldn't save this device's registration") and keeps the saved registration; the next sign-in saves the credentials first and drops the registration only once they are stored, so quitting in between loses neither the device nor its key.
- Account operations run one at a time (below). A sign-in that stalled (fetching its token, or registering) is superseded by a sign-out or another sign-in, and stops with `CancellationError` before it touches the saved registration or the credentials; it can't come back later, replace another user's saved registration, or register under their session. The apps ignore that error: the newer operation reports its own outcome.
- The registration itself can't go out under the wrong identity either: `signIn` hands the Convex client the Clerk user it is for (`setAuth(_:identity:)`, which returns the identity's `AuthScope`), and every call carries the scope current when it was made, captured before its first await. The client checks it atomically when the call is enqueued and again before it is sent; a mismatch fails the call (`authChanged`), never sends it under the new identity. A registration of user A waiting on a socket that hasn't opened yet, or still on its way to the client when B's sign-in changes the identity, fails; it is never sent with B's token, and B's own registration goes out as usual.
- Sign-out runs after everything enqueued before it and before anything enqueued after it, and is never cancelled: a sign-in started while it waits for `devices:remove` waits for it, so sign-out can never erase it. A first registration whose answer was lost (the device never learned its id) is withdrawn by its token: `account:unregister({ token })` removes the device a token names for the signed-in user, and the token is refused for that user from then on either way (`cancelledRegistrations`: the token's hash, the user and why, kept 30 days). `account:register` refuses a refused token for that user (`unauthorized`), so a registration still on its way when the device signed out (sent, not run yet: a retry over HTTP, a replay on a new socket) never creates the device afterwards with a token and key the device discarded. The answer says so (`cancelled: true`), and the device drops the token only on `removed` or `cancelled`: "nothing to remove" alone (an older server) settles nothing, because the registration could still land, so the removal stays recorded. When the server can't be reached, or hasn't confirmed, the device to remove is saved first (`sync.credentials.state.removals.v1`: token, user, server) and withdrawn again the next time the same user signs in on this device; the token of a row that may hold the account's key is never just dropped. A sign-in as another user sets the previous user's device aside the same way instead of forgetting it.
- **A device token is single-use for its lifetime.** Withdrawal alone covered only the registration whose answer was lost. The seventh review found the same orphan after a normal sign-out: R1 is sent and delayed, the retry R2 lands, the device saves its credentials and drops the saved registration (nothing more to withdraw), signs out with `devices:remove` and deletes its keys; then R1 runs, finds no device and no withdrawal, and registers the token again, possibly as the holder of a new library, with a token and key nobody has. Now every path that deletes a device records its token as **retired** in the same transaction, in the same table and index as withdrawals: `deleteDevice` (sign-out, removal from another device, `account:unregister` of a real device, eviction of the 33rd) and `retireLibrary` (the last device out, an expired account), which retires the tokens of the devices the library still has while it still knows the owner, so they stay refused after `legacy:sweep` deletes those devices without one. `account:register` refuses retired and withdrawn tokens alike. A retry while the device still exists gets the same device as before. Owner-less libraries from before accounts have no user to record a token for; their tokens were pairing tokens, never sent to `account:register`.
- Records are bounded. Retirements are never limited (one per device a user ever registered, which the registration rate limit bounds). New withdrawals (a token no device of the user's has, which nothing else bounds) are rate limited per user (`LIMITS.withdrawalsPerUserPerHour`, 10, the `throttles` table) and capped (`LIMITS.maxWithdrawalsPerUser`, 50 unexpired), both answered `rateLimited`; a retry of a token already recorded, withdrawn or retired, is free and still answers `cancelled`. A refused withdrawal leaves the device's removal owed, so it is tried again at the next sign-in; the other owed removals still go (a `rateLimited` entry never blocks the ones after it, so a landed device's unlimited removal isn't held up by a refused withdrawal).
- **A saved registration expires.** Retirements and withdrawals are forgotten after 30 days, so a registration resent later than that could register a token whose device was removed meanwhile, and evict another device from a full account. The eighth review's case: the answer to a first registration is lost, the device keeps it saved, another device removes the row (retiring the token), and the first device stays offline for 31 days; at its next sign-in it resent the saved registration, which the server no longer refused. Now the saved registration records when it was made (`createdAt`, the device's clock) and sends that with every attempt. One made more than 7 days ago (or more than a day in the device clock's future, which means the clock was set back) is never sent again: the device records its token as a removal owed (`sync.credentials.state.removals.v1`; it may have landed), drops it, and registers with a new token and key. The owed removal is `account:unregister` by token, which removes a landed device or records a withdrawal, and is free to retry. The server checks too: `account:register` refuses to create a device from an attempt whose `createdAt` is older than 14 days (`LIMITS.registrationMaxAgeMs`, well inside the 30) or more than a day ahead of its clock (`invalidArgument`, which the device treats as never landed and starts over). A retry of a device that still exists is answered at any age, since it creates nothing. A device whose clock is more than about two weeks off can't register until its clock is fixed; the message says so.
- The app's sign-out (`AccountService.signOut(sync:)`, used by both apps) takes one coherent snapshot of the sign-in (`currentSession()`: the user and the sign-in generation read together before anything is awaited, the Clerk session id after), checks right before asking sync to sign out, with nothing awaited in between, that no sign-in happened since (`isCurrent`), and passes the snapshot's sign-in down (`SyncService.signOut(ifSignIn:)`, a `SyncSignIn`: user and generation). Afterwards it ends that Clerk session only (`ClerkClient.signOut(ifSession:)`): a user who signed in while the device removal waited keeps their session, at Clerk and in sync. The seventh review's case: the snapshot read the generation before awaiting Clerk's session id and the user after, so when B signed in during that await (or the same user signed in again), the sign-out asked sync to sign out B (or the same user's newer sign-in), whose device it removed. Now that snapshot is stale and the sign-out does nothing. Sync is signed in with the generation too (`signIn(auth:userID:generation:)`, from `AccountService.sessionGeneration`), so its own guard compares the user and the generation: a sign-out for an older sign-in neither cancels a newer one that was asked for nor signs one out that ran. The apps' other sign-outs (removed on another device: `SyncService.currentSignIn`; Clerk ended the session: `AccountService.endedSignIn`) carry the sign-in they were started for the same way and do nothing to a newer sign-in.
- **Clerk's notice that a session ended names the session.** `ClerkClient` reports an ended session (`setOnSessionEnded`) with its identity (`ClerkSessionEnd`: the Clerk session id and user), and the notice is queued to the main actor. `AccountService` remembers which Clerk session the shown sign-in is (set with the state by every sign-in, a launch's saved sign-in and a restore) and acts on a notice only when it names that session and user; `endedSignIn` is then that sign-in with its generation. The eighth review's case: A's session ended at Clerk and the notice was queued; before it ran, B signed in and the app connected sync as B; the notice then built `endedSignIn` from what was current, B, so the account showed signed out and both apps signed sync out for B, removing B's device. Now the notice names A's session, which isn't shown any more, and is ignored. `refresh()` likewise applies a restore only to the session it asked about, and only if no sign-in or sign-out happened while it waited.
- A sign-in, the same user's included, is newer than any sign-out still on its way, and the user id can't tell them apart. `AccountService` counts sign-ins (`sessionGeneration`, part of the captured `Session`), and a sign-out checks it before and after every await: before ending the session at Clerk, and after Clerk answered. `ClerkClient.signOut` forgets the session and saves that before it awaits Clerk's removal, and nothing erases the saved state afterwards. The case the sixth review found: sign-out forgot session S1 and waited for Clerk; the same user signed in again (S2); when Clerk answered, the user id still matched, so the saved sign-in was erased and the account showed signed out. Now the generation moved, S2 stays saved and shown.

#### Account operations run one at a time

Every account and key operation of a `SyncService` runs on one serial executor (`AccountOperations`): sign-in, sign-out, registration, applying a device list, claims, releases, rotations, answers, reveals, grants and accepts, Ask Again, removing a device. An operation runs to completion, awaits included, before the next one starts, so none ever acts on another's half-done state. Five reviews in a row found the same class of bug, each a new interleaving: a stale answer or a suspended operation resuming after another one changed the account. The executor removes the class rather than the instances.

- Each operation holds a ticket with the epoch it was enqueued in. A sign-in, a sign-out, `forget()` and `stop()` start a new epoch: older operations that haven't started never run, the running one is cancelled (its calls end with `CancellationError`) and abandoned, and every call checks the ticket after it returns, so a superseded operation changes nothing more even if it is stuck in an await that ignores cancellation. A sign-out is immune: it always runs and is never cancelled.
- Inside an operation, nothing waits for another operation (that would deadlock): a nested `run` executes inline, and follow-up work (the reveal after an answer, the accept after a rotated key opened) is queued and runs next.
- Codes Match and Codes Don't Match only move local state and never await; they run at once when the executor is idle and are queued otherwise.

#### Observations are monotonic

`libraries.keyRevision` grows with every change to the account's key state: the key, its rotation, any device's key row, a device joining or leaving (every `keys:*` mutation, registration, removal, a reset). `devices:list` and `account:register` report it.

- A device ignores a device list whose `keyRevision` is older than one it already applied: two HTTP polls answered out of order, a fetch racing the live query, a list delivered late. Nothing is decided from it.
- The answers to this device's own `keys:claim` and `keys:rotate` report the key revision after the change, and count as observations like a list: an answer newer than the state the change was decided on (and than what this session applied) moves `appliedKeyRevision` on, so a list from before the change is ignored afterwards. An answer that isn't newer proves nothing: a rotation's saved key then stays for a list to settle. Before, a list from before the device's own claim or rotation, arriving after its answer, was applied: the account looked keyless again (and the device claimed again), or showed the old key.
- Recovery material (the saved rotation key `nextLibraryKey`, a pending claim `claimingLibraryKey`) records the revision it was saved at, and is dropped only on a list newer than that which proves it settled: for a rotation, the account moved to a key that is neither the one it was made from nor itself, and no rotated key waiting for this device was made from it (a rotation lands only on the key it was made from, which never comes back); for a claim, the account names another key or none (the claim lands only at the revision it carries, which moved on), unless a rotation waiting for this device was made from the claimed key (it landed; the key is taken and opens it). The account still on the old key, or a list at the claim's own revision, proves nothing and keeps the saved key. A refusal of this device's own call (`forbidden`, and for a claim `conflict`) settles it too. The saved registration and the removals owed are never touched by a device list.
- `keys:release` also carries the revision the device examined (`keyRevision`), and the server refuses the release when anything changed since. On `keys:claim` and `keys:release` the revision is required: every client sends it. The release decision runs as one operation: fetch the list, apply it, decide and call, with nothing in between.

The fifth review's case: A holds K1 with K2 saved (its rotation landed, the answer was lost); B took K2, rotated to K3 wrapped under K2 for A, and left. A delayed list from before any rotation (K1, no rotation needed) used to delete K2 on the spot; A then couldn't open K3, its release passed the server's checks, and as the only holder it reset a vault it could have opened. Now that list is older than what A applied and is ignored; even after a relaunch it is older than K2's saved revision; A opens K3 with K2.
- Every other function still takes `token`, and `authenticate` now checks two things: the Clerk identity is present, and the device the token names belongs to that identity's library. A Clerk session alone can't act as a device, and a removed device's token stops working at once even while its Clerk session lives.
- A library holds at most 32 devices. Registering a 33rd removes the device seen least recently (it gets `unauthorized` and signs out when it next connects).
- Registration is rate limited per user (30 per hour) through the existing `throttles` table, and so are withdrawals of unknown tokens (10 per hour, at most 50 recorded).

### Removal and sign-out

- **Sign Out** on a device: `devices:remove(self)`, then the Clerk session is ended (`POST /v1/client/sessions/{id}/remove`), then local sync data is deleted. Offline, the local part still happens; the server row expires with the library or is removed from another device.
- **Remove** from another device: the removed device's next call gets `unauthorized`, and its token is retired (Devices), so no late copy of its registration can bring it back. The app treats that as "signed out here": it ends its Clerk session and shows the welcome screen. Rejoining means signing in again, which registers a new device, and a new device has to be approved again (the exchange below) before it gets the vault key.
- A removed device that may have the current vault key may still have it, and may still have a Clerk session if it was lost or compromised rather than signed out. The vault key is therefore replaced whenever such a device leaves (Rotation, below), so what it kept opens nothing written afterwards. "May have" is not the device's exchange state: a device that unwrapped a grant can ask again and look like it never had the key. Each key row records `exposedKeyId`, the newest key the device was ever given (made, granted, or wrapped to it by a rotation), and keeps it through any later state; a device counts when it holds the key, has a grant, or its `exposedKeyId` is the current key.
- Removing a device doesn't end its Clerk session. OpenMusic's server has no Clerk secret key, and a device can end only its own Clerk sessions through the Frontend API, so revoking a lost device's session is up to the user: they sign out other sessions on their Clerk account page (the Clerk app's user profile). Until then that session can register a new device, which gets nothing without an approval. A follow-up could do it from the apps with the Frontend API's `/v1/me/sessions/{id}/revoke`, if each device published which session it uses; that wasn't built because a malicious server could then steer the user into revoking the wrong session.
- `unauthenticated` (no identity) is different: the Clerk token expired or wasn't sent yet. The client refreshes the token and retries; it never forgets the device for that.

### Sign-in vault key: device-to-device wrapping

The vault (sealed YouTube Music and Spotify sign-ins) keeps its format: AES-GCM under one 32-byte **vault key** per library (still `LibraryKey` in code), fingerprint `keyId` on the library row, revisions bound into the authenticated data. What changes is how the key reaches a device: no QR code, no link.

State per device, in the table `deviceKeys` (one row per registered device):

| `state.kind` | Meaning |
| --- | --- |
| `holder` | This device has the vault key. `rekey` carries a rotated key it hasn't taken yet. |
| `requested` | This device has no key and asks for it. `exchange` is its verification exchange (below), absent until it commits. |
| `denied` | A holder tapped Don't Allow. No prompts until the device asks again. |
| `granted` | The holder that ran the exchange wrapped the key to this device; the device hasn't confirmed yet. Carries the wrapped key and the exchange's commitment. |

#### First device and claims

The first device of a library proposes a fresh key at registration and becomes `holder`. Mutations are serializable, so with two first devices at once exactly one key wins and the other device becomes `requested`. `keys:claim` sets a key only for a library that has none (every device that could open the vault is gone, see Reset), never for a library that has one, and never a key the library used before (`retiredKeyIds`). A device claiming always generates a fresh key.

The claimed key is saved in the device's credentials (`claimingLibraryKey`, inside `sync.credentials`, so no new Keychain account) before `keys:claim` is sent, and the device sends the same key again until the claim is settled. If the server took the claim and the answer was lost, or the app quit, the account's only key isn't lost: the next device list (this session or the next launch) adopts it when the server names it, and drops it when the server names another key. Adopting it is safe whatever the server says, since only this device ever had it. A claim refused with `forbidden` never landed (the account has a key again, or this one is retired), so its key is dropped and the next claim makes a new one.

A claim is a compare-and-swap on what the device examined: `keys:claim({ keyId, keyRevision })` carries the key revision of the state in which the device saw no key (`claimingLibraryKeyRevision`, saved with the key; a retry sends the same one), and the server refuses it with `conflict` when the revision moved since, changing nothing. So a claim can land only right after the state it was decided on. The sixth review's case: the phone claimed C for a keyless account, but the claim was still on its way; the iPad joined with a key of its own, the phone saw it and dropped C, the iPad left (keyless again), and then the phone's claim ran. It used to land, making the phone the holder of a key it no longer had, with no way back. Now it is refused, and so `conflict` settles a claim like `forbidden`: no copy of it can land later.

#### Approving a device: the verification exchange

The server relays four messages between the asking device B and a holder A. Everything it relays is public; neither device trusts it for anything but transport, and each computes the code from its own record of the exchange (`KeyLedger`, kept in the credential store as `sync.credentials.state.keys.v1`).

1. **Commit.** B makes a secret 32-byte nonce `nB` and calls `keys:request({ commitment })` with `commitment = SHA-256("medley.key-exchange.v1.commit" ‖ pkB ‖ nB)`, base64. It does this by itself after registering, and again (with a new nonce) when its exchange was dropped.
2. **Answer.** Every online holder sees the commitment in `devices:list` (with B's public key). A, having seen it, records its nonce `nA` for that commitment and calls `keys:answer({ deviceId, commitment, nonce: nA })`; the server adds A's device public key `pkA`. The first holder to answer runs the exchange; the others get `conflict`. `nA = HMAC-SHA256(HKDF(skA, info: "medley.key-exchange.v2.answer-nonce"), libraryId ‖ B's id ‖ pkB ‖ commitment ‖ A's id ‖ pkA)` (each length-prefixed; keys and commitment as bytes, so a re-encoded string is the same request): unpredictable without A's private key, and always the same for the same request, so A never gives a second nonce for one request, even after its record of the first is gone. It covers every field of `T` that is fixed before A answers (`nB` is fixed by the commitment), so no field can change without changing the nonce. The first version covered only the library and the commitment, while the code also covers B's id: once A's ledger had pruned an answer (a day later), a server could show the same commitment as a made-up device and get the same `nA`, having searched offline (about 2.6 million tries, seconds of work) for a device id whose code matched one it had fixed on the real B. Now the same commitment under another id, or with another key, gets an unrelated nonce, so each such answer is a fresh one-in-a-million online try counted against A's hourly limit, and pruning the ledger after a day gives nothing away. A `conflict` reply doesn't erase the record either: the server has seen the nonce by then, so the answer stays in the ledger, counts toward the hourly limit, and isn't sent again.
3. **Reveal.** B, having recorded A's answer (the first one it saw; a different answer shown later is ignored), calls `keys:reveal({ commitment, nonce: nB })`. A checks that its own nonce came back unchanged and that `SHA-256(domain ‖ pkB ‖ nB)` equals the commitment. An exchange that doesn't check out is never shown: A calls `keys:deny`, counts a failure and shows a warning (below).
4. **Compare.** Both devices show `code = 6 digits of SHA-256("medley.key-exchange.v1.code" ‖ T)`, where `T` is SHA-256 over the library id, B's id, `pkB`, `nB`, A's id, `pkA` and `nA` (each length-prefixed). A asks "Allow B…? Code 482 913"; B shows the same code with Codes Match / Codes Don't Match.
5. **Grant.** On Allow, A seals the vault key with `wrapKey = HKDF-SHA256(X25519(skA, pkB), salt: T, info: "medley.key-grant.v2|<libraryId>|<B's id>|<keyId>")`, `wrapped = base64(AES.GCM.seal(vaultKey, wrapKey).combined)`, and calls `keys:grant({ deviceId, keyId, wrapped, commitment })`. The server takes it only from the holder that answered, for that commitment, after the reveal, and not while the key is being rotated.
6. **Take.** B opens the grant with `X25519(skB, pkA)` and its own `T`, checks the fingerprint, and keeps the key only once the listener also tapped Codes Match on B (either order). Then it calls `keys:accept({ keyId })` and becomes `holder`. Until then B has no key: it imports nothing and uploads nothing, including sign-ins it already had before it asked. Codes Don't Match, or a grant that doesn't open, ends the attempt; Ask Again starts a new one.

Limits, on the devices (a server can't enforce anything against itself):

- A holder answers at most 6 new commitments an hour (`SyncService.answersPerHour`) and stops answering after 5 failed or refused exchanges in a day (`failuresBeforePause`). Every answer issued counts, whatever the server replies to it (`conflict` included), and the count lives on the device (`KeyLedger.answers`, kept a day), so nothing the server says frees a slot. Answers that waited are given on the next device list change or heartbeat once the limit allows.
- An asking device starts at most 3 exchanges an hour by itself (`automaticAttemptsPerHour`); more need Ask Again.
- `keyWarning` (Settings › Account, on holders) says when an exchange was changed on the way, or when 2 or more exchanges failed or were refused in a day, or when answering is paused.
- The server also rate limits `keys:request` to 20 per device per hour, against a device (not the server) spamming prompts.

#### Rotation

When a device that may have the current key (a `holder`, `granted`, or any device whose `exposedKeyId` is the current key) is removed, signs out or is evicted, and other devices still can open the vault, the server sets `libraries.keyRotation`. While it is set, `vault:put` and `keys:grant` are refused. Every holder that sees `rotationNeeded` in `devices:list` rotates at once (one wins, the others get `conflict` and receive the new key instead):

- It makes a fresh key `K2` and saves it first as `nextLibraryKey` (so a rotation whose answer was lost isn't lost with it). A saved `K2` settles from a device list newer than the one it was saved on (Observations are monotonic): the server naming `K2` means it landed; a waiting rotation made *from* `K2` means it landed and another holder already rotated again (this device's answer was lost, it quit, and another holder took `K2` and rotated to `K3` meanwhile), so `K2` is kept and opens that wrap (a wrap is accepted when made from the held key or from the saved one; only holders have either); the account on a key that is neither `K1` nor `K2`, with nothing waiting made from `K2`, means it can't land any more, and `K2` is dropped. The account still on `K1` keeps it (the next rotation reuses it).
- It wraps `K2` to every other holder: an ephemeral X25519 key `e`, `wrapKey = HKDF-SHA256(X25519(e, pkH) ‖ K1, salt: e.public ‖ pkH, info: "medley.key-rotation.v1|<library>|<device>|<K1 id>|<K2 id>")`, `wrapped = base64(e.public ‖ AES.GCM.seal(K2, wrapKey).combined)`. Only that holder can open it, and only a device holding `K1` could have made it.
- It re-seals every sealed vault row under `K2` at its next revision (a row it can't open becomes a tombstone).
- It re-seals every settings value under `K2` (`settings`, each at the `updatedAt` it read; one that doesn't open with `K1` is deleted). Settings are therefore never under a retired key; what each device publishes about itself (playback, queue) is re-sealed by that device as soon as it holds `K2` (the server still takes `K1` blobs of those kinds for 10 minutes, `previousKey`, and readers skip them).
- `keys:rotate({ fromKeyId, keyId, wraps, vault, settings })` applies all of it in one transaction, checked against the current holders and vault revisions (`conflict` otherwise, and the device looks again). It retires `K1`, puts each wrap on its holder's row as `rekey` (and marks those holders and itself exposed to `K2`), drops unaccepted grants (those devices ask again), and moves holders that still had an older `rekey` waiting to `requested` (they can't open a wrap made with a key they never took).

A holder that was offline through two rotations comes back holding `K1` while the account uses `K3`, listed as `requested`. It keeps `K1` and asks nothing by itself: the server saying so is never enough to make a device drop a key. Its status is `outdated` ("Your sign-ins changed while this Mac was away", with **Ask Again**). Ask Again drops the old key and runs the normal exchange with a holder of `K3`, codes and all. `requestKeyAgain()` drops a held key only in that case (a held key that isn't the account's, the server listing this device as `requested` or `denied`, and no rotation or claim of its own pending).

A device the server still lists as a `holder` can end up in the same place: its key isn't the account's and nothing it has leads to the current one (no rotation or claim of its own pending, no waiting rotation made from a key it has, or one that didn't open). As a holder it could never ask again, and an account whose only holders are like it would never be reset. Before giving up anything it looks again: the device list that suggested this may have arrived late (two HTTP polls answered out of order), and a device that holds the key a waiting rotation was made from must take that rotation, not drop it. So the device fetches `devices:list` afresh, applies it (which tries every key it holds, the current one and a rotation of its own it never heard back about, against the rotated key waiting on its row), and only if it is still stranded calls `keys:release({ keyId, accountKeyId, rekeyKeyId, keyRevision })`: the key it holds, plus what it examined, the account's key and the rotated key waiting for it (null for none). The release is a compare-and-swap: the server refuses it (`conflict`) when that is the account's key, when the account's key isn't `accountKeyId`, when the rotated key waiting on the device's row isn't `rekeyKeyId`, or when the account's `keyRevision` moved since the device looked, and changes nothing then. The fetch, the decision and the call run as one account operation. The case the fourth review found: A's list from while the account used K1 is delayed; A rotates to K2; B takes K2, rotates to K3 (wrapped for A under K2) and leaves; A then reads the late K1 list while holding K2. It used to release K2 at once, and the server dropped the K2→K3 envelope A could open and, with no holder left, cleared the vault. Now A's fresh look finds K3 waiting, opens it with K2 and sends no release; and a release built on the stale list would be refused anyway. Otherwise the server makes the device `requested` with no exchange, restarts exchanges it was answering, and resets the key when no device left can open the vault (`resetIfStranded`). The device then shows `outdated` and keeps its key until the listener taps Ask Again, as above; on an account left with no other holder, the reset lets it claim a fresh key. A malicious server can trigger this by naming a key the device doesn't have, which is denial of service it could already cause; it still gets no key.

A holder takes a `rekey` only if it opens with its own key pair and the key it holds, and its fingerprint is the library's; then it calls `keys:accept`. Anything else (a wrap the server made) is refused and counted, and the held key stays.

#### Reset: no device can open the vault

When the last device that could open the vault leaves, nobody can open it. The server clears `keyId` (and retires it), drops `keyRotation`, moves every remaining device to `requested`, deletes the settings (sealed under the lost key; the next device to claim a key fills them in from its own values), and changes the vault rows without deleting them: each sealed row becomes **cleared** (`cleared: true`, no blob) at its next revision, and a tombstone stays a tombstone. Revisions only ever grow, so every device's record of the revision it applied stays valid:

- A device that applied a sign-out at revision 5 still has it applied; its next write is based on the stored revision, not 0.
- A cleared row isn't a sign-out: a device keeps its own sign-in, notes the revision, forgets what it last synced, and uploads its sign-in again once it has the new key.
- An old blob can never come back at a revision a device already passed.

The next device to notice claims a fresh key and uploads its local sign-ins; the others then go through the exchange with it.

The same reset happens when the key is stranded without a device leaving: A granted B, A signed out (B's grant still counts, so the key stays and must be rotated), then B tapped Codes Don't Match and Ask Again. `keys:request` moved B back to `requested`, and now no device can rotate, grant or write the key, while `keys:claim` is refused because the account has one. `keys:request` checks for this after every request (`resetIfStranded`) and resets the key; B, which never took it, then claims a fresh one. Accounts an older server already left stranded are reset by the next heartbeat of a device without the key (holders' heartbeats skip the check).

#### Pinning

A device that holds a key never replaces it from a grant. Its key changes only by a rotation it can open with that key, when it claims a fresh key it made itself for a library the server says has none (the server learns nothing either way), or when the listener taps Ask Again on a device whose key is out of date (Rotation), after which the new key comes only through the exchange. While the server names a different key than the one held, or the key is being rotated, the device writes nothing to the vault (`vaultWritesPaused`) and shows the mismatch.

#### What a malicious server can and can't do

The threat model includes a compromised hosted server and a malicious custom server URL. Such a server sees every message between devices and can rewrite any of them, invent devices and grants, and answer any query however it likes.

- It never learns the vault key, a sign-in, or what anyone plays or searches for: vault rows, playback, queues, takeovers, command messages and settings are AES-GCM under keys derived from the vault key (`docs/sync-design.md`, "What the server can see"); grants are sealed under a key derived from two devices' X25519 private keys, which never leave them; rotations are sealed to a device key. The server stores fingerprints, public keys, nonces and sealed blobs only.
- It can't put itself between two devices without the listener seeing different codes, except by chance. To do it, it must show A a commitment of its own before it sees `nA`, and show B an answer of its own before it sees `nB`, so each code it gets is fixed before the value that randomizes the other is known. Each attempt succeeds with probability 1 in 10⁶, it can't search offline as it could when the code came from a static public key, a mismatch is visible to the listener, and the devices limit and report attempts.
- It can't grind A's code online either. With B's code fixed (an answer of its own shown to B, B's reveal in hand), it could keep asking A for answers until one gives the same code, discarding misses. A gives one nonce per request ever (the request being everything the code covers that is fixed before A answers, B's id included) and at most 6 answers an hour in all, whatever the server replies, so that takes on the order of 10⁶ hours. Showing an answered commitment again under another device id gets a new, unrelated nonce, never one it already knows.
- It can't give a device a key of its own: a new device takes only a grant that opens under the exchange the listener confirmed on it, which needs the holder's private key; a holder never replaces its key from a grant, and takes a rotated key only when it was made with the key it holds. So it can't collect sign-ins uploaded later, including sign-ins a new device had before it asked.
- It can't steal the Clerk client token: the saved sign-in is bound to the Frontend API origin it was made with (Server choice).
- What it can do: deny service (drop or refuse anything, hide devices, claim a library has no key so a holder starts over with a fresh key and the vault's sign-ins have to be uploaded again), and see metadata: device names, models, when devices are online, where playback is (position, playing or paused, volume, shuffle, repeat, the song's length), command kinds with their numbers, setting names and when they changed. It can also replay an older sealed value of the same device in the same place, or withhold updates. It can also make devices sign out of a service by writing a tombstone, as any device token holder already could.
- Anyone holding the user's Clerk session can register a device and ask for the key, and still needs a holder to tap Allow with matching codes. That is the same trust as "someone who can sign in to your account".

### Server choice

- The hosted server is the default: `OpenMusicSyncURL` in Info.plist, as today (production `insightful-roadrunner-835` for Release builds, dev `sensible-barracuda-214` for Debug).
- A custom server is one URL saved per device in UserDefaults (`syncServerURL`): an origin only (scheme, host, optional port; a path, query or fragment is refused, since the client builds its own paths and the socket would drop a path). `https://` on any host and port. `http://` only for this machine and the local network (localhost, 127/8, ::1, 10/8, 172.16/12, 192.168/16, link-local, unique-local, `.local`), which is what the apps' `NSAllowsLocalNetworking` lets through; Tailscale addresses (100.64/10, fd7a:115c:a1e0::/48) over http are refused with their own message, since ATS blocks them and Tailscale Serve gives the server an https address. `SyncServer.validate` gives the reason for each refusal; an ATS refusal from the system reads as `blockedHTTP`. Settings shows the host with its port (`SyncServer.displayName`).
- `config:get` (public query, no identity needed) returns `{ auth: { kind: "clerk", publishableKey } }`, or `{ auth: { kind: "notConfigured" } }` when the server has no `CLERK_PUBLISHABLE_KEY`. The app decodes the Frontend API host from the publishable key (`pk_test_`/`pk_live_` + base64 of `<host>$`). So a self-hoster gives OpenMusic one URL and nothing else.
- The decoded host must be a plausible public DNS name, used over https: lowercase letters, digits and inner hyphens, at least two labels, a last label that isn't a number, no port, path, user info, IP address, `localhost` or `.local`. Anything else counts as not configured.
- The server is asked for the key at every launch, so the saved Clerk sign-in (`ClerkState`) records the Frontend API origin it was made with. When the server's configuration names a different origin, the saved state is dropped without being sent anywhere: the client token never reaches the new host. The account shows as signed out with a notice ("This server now signs in through a different service (host), so OpenMusic signed you out instead of sending your sign-in there…"), and sync signs out (`onSessionEnded`). Saved state from before origins were recorded is treated the same way.
- Before saving a custom URL the app calls `config:get` on it; a server that doesn't answer or isn't configured is refused with the reason.
- When `config:get` can't reach the server at launch (offline), a saved sign-in still shows, and `AccountService` tries again by itself with backoff (2 s up to 5 min), when the network comes back (`NWPathMonitor`, only while the configuration is missing), when the app returns to the foreground, and on **Try Again** next to the problem. Once it loads, `onReady` lets the app connect the saved sign-in.

### Clerk on native: the decision

OpenMusic drives Clerk's Frontend API itself (`Sources/MedleySync/Account/ClerkClient.swift`) instead of adding the official SDK.

- The official `clerk-ios` package does support both platforms (iOS 17+, macOS 14+). But its `Package.swift` pulls in Nuke, PhoneNumberKit, Mocker, swift-concurrency-extras and swift-snapshot-testing, and its `ClerkKitUI` brings a full UI kit. OpenMusic has no dependencies and builds the Mac app with plain SwiftPM and the iOS app with XcodeGen; five transitive packages plus their resolution on the shared build Mac are a real cost for the two flows we use.
- The flows OpenMusic needs are small and documented: `GET /v1/environment` (which social providers are on), email code sign-in and sign-up (`/v1/client/sign_ins`, `/prepare_first_factor`, `/attempt_first_factor`; `/v1/client/sign_ups`, `/prepare_verification`, `/attempt_verification`), OAuth through `ASWebAuthenticationSession` (`strategy: oauth_google`/`oauth_apple`, `redirect_url: openmusic://oauth-callback`, then reloading the sign-in with `rotating_token_nonce`, or a sign-up with `transfer: true` for a new user), the Convex token (`POST /v1/client/sessions/{id}/tokens/convex`) and sign-out (`POST /v1/client/sessions/{id}/remove`).
- Native mode as the SDK does it: every request adds `_is_native=true`, sends the saved client token in `Authorization` (no cookies, no `Origin`), and saves the `Authorization` header of every response as the new client token. The client token is kept in the Keychain (`sync.credentials.state.clerk`), with the origin it belongs to.
- `ClerkClient` is an actor, but its calls interleave across awaits. Each request records the session generation it started in; sign-out, an ended session and a new sign-in start a new generation, and an answer for an older one is dropped (`ClerkError.stale`): its rotated client token isn't saved and it restores nothing. Sign-out forgets the session locally first and then ends it at Clerk with the token it had, so a restore or token refresh still in flight can't bring it back.
- **A restore never switches sessions.** A Clerk client can hold several sessions. At launch `restore()` accepts only the saved session; when Clerk no longer lists it as active, the client signs out (and reports the saved session as ended) even if another session on the client is active, and a sign-in takes exactly the session it created. The eighth review found the launch moving silently to another active session, possibly another user: the account showed that user under the old sign-in generation while sync stayed signed in as the saved one, so the new user's JWT would fail routing and a sign-out captured earlier still looked current. Of the two fixes (treat the switch as a sign-in, bumping the generation and moving sync from one user to the other, or refuse it), OpenMusic refuses it: it is rare (OpenMusic ends its session at Clerk when it signs out, so a second active one comes from elsewhere), a sign-in the listener didn't make shouldn't start syncing their sign-ins under another account, and it needs no second path that moves sync between users. The account shows as signed out with a notice naming the other sign-in ("Your sign-in on this device ended. OpenMusic signed you out instead of switching to another sign-in it found (name). Sign in again to choose the account."), the apps sign sync out for the saved sign-in as for any ended session (its device is removed now, or owed until that user signs in again), and signing in again is a normal sign-in with a new generation.
- **A required password.** Clerk's default sign-up requires a password, and only its dashboard can make it optional (the Backend API has no setting for it). When an email sign-up's only missing field after the code is `password`, `ClerkClient` sets 32 random bytes (base64url) with `PATCH /v1/client/sign_ups/{id}` and finishes; the password is never shown, saved or logged, and OpenMusic goes on signing in with codes. Any other missing field is still refused with an explanation.
- Cost of the choice: Clerk's API can change under us (we pin `clerk-api-version`), and features like passkeys, MFA and native Sign in with Apple need code of our own. Native Sign in with Apple (`oauth_token_apple` with an `ASAuthorizationAppleIDCredential` identity token) needs the Sign in with Apple entitlement, which the current wildcard signing profile can't carry, so for now Apple goes through Clerk's web OAuth like Google.

### Convex client authentication (`Sources/MedleySync/Convex`)

- `ConvexClient.setAuth(_ provider: (any AuthTokenProvider)?)`. `AuthTokenProvider.token(forceRefresh:)` returns the Convex JWT or nil when signed out.
- On every socket open: `Connect`, then `Authenticate { tokenType: "User", value, baseVersion: 0 }` (identity version 1), then `ModifyQuerySet` and the replayed mutations, the order the npm client uses. Without a provider nothing is sent and the identity stays version 0.
- **Refresh.** The client reads `exp` and `iat` from the JWT and fetches a new token 10 s before `exp` (at once if it is already that close), then sends `Authenticate { baseVersion: current }` on the open socket. Queries rerun on the server with the new identity; transitions carry the identity version as today.
- **AuthError.** On `AuthError` the client closes the socket, asks the provider for a fresh token (`forceRefresh: true`) and reconnects with it. If the provider returns nil, or a fresh token is refused twice in a row, the client reports `authFailed` and keeps the socket open unauthenticated; `SyncService` then shows "signed out" instead of retrying in a loop.
- **HTTP fallback.** `POST /api/query` and `/api/mutation` send `Authorization: Bearer <jwt>`.
- **A call carries only its own identity's token.** When `setAuth` names a new identity, the old identity's token is forgotten and the open socket drops its identity (`Authenticate { tokenType: "None" }`) at once, before the new token is fetched. Calls of the new identity wait (unsent) until its token is here and, on the socket, has been sent ahead of them (`flushHeld`); if it never comes they time out. A token is used only if its `sub` is the identity `setAuth` named (the Clerk user id), checked when it is adopted and again before every HTTP call, and a socket call goes out only on a socket authenticated with that very token. The client decodes `sub` without checking the signature: this is a routing guard for its own calls, not verification. Convex verifies every token and is the authorization boundary; a forged token passes the client's check and still gets nothing from the server. Before, A→B with B's token fetch failing (offline) left A's token in place: B's registration went out on the socket still speaking for A, or over HTTP with A's cached JWT, and B's device registered in A's library. A provider that says signed out (nil) lets waiting calls go out without an identity, as before.
- **Calls belong to an identity.** `setAuth(_:identity:)` takes who the provider signs in (`SyncService` passes the Clerk user id) and returns its `AuthScope`. `mutation(_:args:scope:)` checks the scope inside the actor when the call is enqueued and fails with `authChanged` if it isn't current, so a call made for one identity never takes on the next one while it is on its way to the client. Each mutation records the identity it was made under. Cancelling the calling task ends a mutation with `CancellationError` (unsent, it never goes out; sent, its answer is ignored). When the identity changes (another user, or nil on sign-out), mutations not sent yet fail at once with `ConvexClientError.authChanged`, and one already sent under the old identity is never sent again: a replay on the next socket, or a retry over HTTP, would carry the new identity, so it fails with `.authChanged` instead. An HTTP mutation checks the identity again after fetching its token. A new token source for the same user keeps queued mutations.
- **Live query results belong to their session.** `SyncService` applies a result of `devices:list`, `vault:list`, `settings:list`, `playback:list`, `commands:incoming` or `commands:outgoing` only while the session it was subscribed for (its device token) is still the current one and its task wasn't cancelled, checked right before applying it. A result already on its way to the main actor when the session ended used to be applied after it, to the next session (a vault tombstone of A's library could sign B's provider out).

`cancelledRegistrations.reason` is optional for the same kind of reason: the dev deployment already holds rows written before it existed, and a required field would make the schema push fail on them. Every reader treats a missing reason as `withdrawn`, so those rows refuse their tokens and count toward the per-user withdrawal cap. Deploy order, per deployment (dev first, then production): (1) push this schema and code (`reason` optional); (2) run the backfill, `npx convex run account:backfillCancellationReasons` (through `scripts/convex.sh`), which patches `LIMITS.sweepBatch` rows per run and schedules the next run until the table is done, and is safe to repeat; (3) once it has finished on both deployments, a follow-up change makes `reason` required. Step 3 is not in this change.

`owner` is optional in the schema only because libraries from before accounts exist in the dev and production deployments and must validate on push. New code never creates a library without one, and the legacy sweep deletes those that lack it. A later change can make it required once both deployments have swept.

Crons kept: commands, throttles, settings writes (unchanged), and the hourly library sweep. Libraries now expire after 60 days with no device seen (one limit; the 7-day "never paired" limit goes, since a one-device library is normal now). Coming back after that is harmless: the next launch registers again as the first device of a new library.

Deleting a library (the last device left, or it expired) **retires** it: the owner is detached at once, so its tokens stop working and the user's next device starts a new library, and `legacy:sweep` deletes the rows in the background. `legacy:sweep` runs every 10 minutes and right after a library is retired. It deletes owner-less libraries with everything below them (vault, settings, settings writes, key rows, playback, then each device with its queue and commands, then the library), then invites and old counters, at most 1,000 rows per run in all (`LIMITS.librarySweepRows`), however large one library is: invites take from what the libraries left of the budget, and counters from what the invites left. A run that reaches the budget schedules the next, which picks up from what is still in the database.

## Migration to sealed content

The sealed playback, queue, command and settings fields replace the plaintext ones, and the schema push validates every stored row, so those tables must be empty when the new code is pushed. No released app wrote them. On dev (`sensible-barracuda-214`) all four tables (and `settingOps`) held no rows at the push on 2026-11-07, so nothing had to be cleared: the e2e runs sign their devices out, which deletes their rows. For any deployment that has rows (production, a self-hosted server), clear `playback`, `queues`, `commands`, `settings` and `settingOps` first (dashboard › Data › the table › Clear table), then deploy. Apps that published plaintext stop working against the new server until they are updated: their writes are refused as invalid arguments.

## Migration of paired devices

The simplest acceptable story: existing paired devices are asked to sign in once, and old library data expires.

- When the new backend is deployed, old libraries have no owner. Old builds' tokens still name devices in them, but `authenticate` refuses them (`unauthorized`), so an old build shows "This device was removed from your devices" and unpairs. The legacy sweep then deletes those libraries with their playback, vault and settings rows within minutes.
- A new build finds old `sync.credentials` without a device key pair; it drops them (they belong to a pairing), keeps its local YouTube Music and Spotify sign-ins untouched, and shows the welcome screen once.
- Synced settings and recent searches stay on each device locally; the first device to sign in fills the account with its values (`ifAbsent`), as a first device does today.
- Deploy order: the dev deployment first (its env vars set), then production. Both need `CLERK_JWT_ISSUER_DOMAIN` set before the push, or Convex refuses `auth.config.ts`.

## Saving before acknowledging (review 10)

A device saves a key it was granted, or a rotated key it opened, to its credential store before it sends `keys:accept`. The server deletes the grant (or rotation envelope) and lists the device as a holder as soon as it hears the accept, so a key that lived only in memory would be gone after a relaunch, and a holder can't Ask Again. When the save fails, nothing is acknowledged: the opened key, the attempt and the server's grant all stay, and the next device list tries again. In the owed-removal loop, `invalidArgument` (a malformed saved token, which can never name a device) drops that entry and goes on; `rateLimited` keeps it and goes on; anything else stops the pass until the next sign-in.
